# n=4 选参与迁移交付记录（2026-11-14）

> 本文保留r1交付和选参记录。迁移路径与校验流程已按用户要求简化为r2，当前操作以[精简记录](迁移路径与校验精简记录_20261114.md)和中转目录的TRANSFER.md为准；不再要求逐文件代码/模型核验。

本轮做两件事：用已完成的 naive n=4 实验选择 Actor 奖励参数，以及准备迁往单卡 H200 的代码和数据。完整数值、测试结果与交付命令见 [本轮报告](../../reports/gad_n4_selection_migration_20261114/README.md)。没有启动正式 Actor 训练、推送 GitHub 或连接新服务器。

## 1. naive 已完成，可以选参

`rubric_naive_n4_06b_17k_v2` 已从 Warmup271 完成到 GAD542，即新增271个更新，用时约79.52小时。最终 checkpoint 验证通过；影子日志覆盖272–542全部步骤，共69,376条学生回答、17,344个四回答组，没有重复步骤记录。

这里的“影子”是指：训练时只用原对抗奖励更新 Actor，同时记录 Critic 的 adv、c、p、e 四个分数。现在可以在这些记录上重算：假如加入 rubric，哪些回答的排序和优势会改变。这个过程只用 CPU，不重采回答、不训练模型。

本轮严格沿用三组方案第6节：按题目哈希分选择集和复核集；比较 `c+p-e` 与只用 `c`，权重为0.25、0.5、1、2；各自的标准差下限 τ 由选择集的第25百分位确定。τ=0和中位数只作敏感性参考，不参与正式选择。没有候选通过时如实报告，不临时放宽约束。

本次唯一通过的候选是Actor只用c、w=0.25、τ=0.045992180705070496；选择集和复核集都刚好达到80%方向比例，主要净修正来自正确完成回答与错误截断回答之间。完整c+p−e未通过。Critic仍保留c/p/e三维辅助损失。

选参结果只描述这批固定回答上的奖励变化，不能直接证明 Actor 最终正确率提高。当前 Actor launch 中的占位参数没有被自动替换，`rubric.actor_reward_selection_confirmed` 仍为 false。按原计划，用户确认分量、权重和 τ 后才冻结并开始第三组。

最终训练内 dev 验证有1条未决评分，`acc=null`，临时下界为70/512（13.67%）；这不是训练失败，也不是完整八任务评测结果。它不阻挡本次目录整理和离线选择。

## 2. 本机 Actor 和 H200 重跑是两条安排

- **本机第三组**：沿用原三组方案，共享 `rubric_direct_06b_17k_20261026` 的 Warmup271；不要接着 naive 的最终542继续训练。参数参考本次选择结果，再由用户确认。
- **H200 后续实验**：从初始模型重新开始。一次公共 SeqKD、baseline 和 rubric 各一份新 Warmup，再跑三组 GAD。Actor 使用新 rubric Warmup；按新 naive 日志重新选择参数。本机选参值只作为历史记录，不自动冻结成新机正式值。

训练输出预算仍为8192，使用完整17k Teacher 数据，保留错误或截断回答。本轮没有恢复 correct-nontruncated 筛选。

交付目录在 `reports/gad_n4_selection_migration_20261114/`：

| 位置 | 用途 |

训练数据包约114.49 MiB，补充依赖包约2.74 MiB。模型权重、旧 Warmup、旧 run、优化器、Judge 缓存和整个 Conda 环境均不迁移。Qwen模型在目标机下载，共同单头 Critic 在目标机按 seed42 重建。旧模型 revision 未能确定的地方保留“不明”，提供现有文件哈希，不编造下载 commit。

源码目录有三处很小的迁移修正：

1. `.gitignore` 明确排除评测数据目录和 `verl.bundle`，它们走中转包；不是删除这些本机资产。
2. `package_runtime.py` 补入 `gad/deepscaler`、其安装文件和许可证，以及发布说明引用的少量 README。它们原来在本机存在，但不在导出白名单中。固定 backend 仍存在 deepscaler 导入，不能在迁移时漏掉。

发布副本保留正式 train/sample/evaluate/scoring/rubric、配置、测试、环境记录、小型依赖源码和关键报告摘要。没有把旧 `eval_fix`、`judge_fix` 候选树、生成的 backend、历史模型和整个 reports 塞进 Git。原服务器的这些文件仍在原位置。

3. n=4 CPU测试改用已有的模型身份和小数据夹具，避免纯代码副本必须先拥有旧服务器的真实模型、训练数据才能运行测试；原断言和训练保护不变。

## 4. 哪些精简暂时没有做，为什么

| 对象 | 本轮处理及原因 |
|---|---|
| `eval_fix` 和旧 GPT5/7B shell | 已于11月12日归档；发布副本保留归档说明，正式评测不再依赖候选实现 |
| `judge_fix` | 不发布；本机旧 rubric Warmup 的冻结配置仍引用其中的文件，第三组还要复用它，因此不移动原路径 |
| 旧 backend/worktree | 不发布，通过 bundle 重建；本机历史依赖保留，不为腾目录批量删除 |
| 五份完整 launch | 已相对路径化，保留为本机可复现配置；此时拆分会增加第三组与前两组的对照审核成本。新机配置在部署时另建 |
| 离线 rubric、旧证据协议 | 当前仍有测试、导入或身份哈希依赖，暂时保留源码。强行删除会扩大这次修改范围，可能改变 Judge 身份 |
| `gad/deepscaler` | 很小且仍被固定 backend 导入，补入迁移包，不改 vendor 代码以追求删目录 |
| replay | 当前 n=4 实验关闭；代码、配置、恢复逻辑和测试继续保留 |

因此，本轮精简主要发生在**发布内容范围**，而不是把原实验目录删到最小。BT、rubric BCE、Actor 奖励公式、数据游标、Teacher 预取和阶段交接均未改动。

## 5. 验收与仍需在新机做的事

发布副本在独立目录重建固定后端，并运行适用的 CPU 回归及扩展评测测试。五份 launch 从 `/tmp` 调用解析，与原目录相比只改变项目根路径；相对软链接不指向原项目。两个中转包已实际解包，31个文件的哈希与原文件一致。最终测试数量、可选跳过项和 commit 以本轮报告为准。

这些检查证明的是“交付内容齐全、迁移没有改变已检查的 CPU 行为”，不等于 H200 已能直接训练。目标机还需要安装匹配环境、下载模型、重建 Critic、生成单卡配置并处理 Judge 共卡限制，再做阶段交接与保存恢复的小规模 GPU 验证。这些仍遵循 [H200迁移计划](GAD_n4单卡H200迁移计划.md) 第5节，留到迁移后完成。

发布命令必须在独立 `publish/LMOps` 中执行；不用在当前实验根目录 `git add .`。代码通过现有 GitHub 仓库发布，中转包通过个人电脑在两个 VS Code Remote-SSH 会话之间转移，无需两台服务器相互连接。
