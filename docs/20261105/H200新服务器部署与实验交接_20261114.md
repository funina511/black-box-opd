## 2. 框架设计：每个模型负责什么

### 2.1 数据到训练的主流程

```text
sample：题目 → Teacher 回答 → 训练 Parquet + Teacher 索引
                                  │
                     共同初始学生 Qwen3-0.6B
                          ┌───────┴────────┐
                          │                │
                      SeqKD 基线        Warmup
                      独立训练          Actor + Critic
                                           │
                                           ▼
                                          GAD
                          Student 同题生成 n=4 个回答
                          Critic 比较 Teacher / Student
                          Actor 用组内优势进行策略更新
```

- **Teacher**：提供已有回答池，本轮不在线部署原 Teacher 模型。
- **Actor / Student**：Qwen3-0.6B，负责生成回答。当前训练和评测采用 non-thinking 提示。
- **Critic / 判别器**：共享语言模型主干，原版只有一个对抗评分头；rubric 版本有四个评分头。
- **Judge**：独立 Qwen3-8B 推理服务，启用 thinking，给选中的回答提供过程标签。它不参与梯度更新，也不替代 Critic。
- **Reference**：Actor 更新中的 KL 参考模型；保留原框架定义，不改成 Judge 或 Teacher。

SeqKD 使用 Teacher 回答进行独立蒸馏，不作为 Warmup 的初始化来源。Warmup 从初始学生和共同 Critic 初始化出发，并继续更新模型；rubric 辅助监督从 Warmup 开始，而不是到 GAD 才突然出现。

**不要把 Warmup 说成“完全不生成学生回答”或“只训练冻结 Actor 的 Critic”。** 以现有阶段后端的真实执行为准；短测还需要注意前期 `critic_warmup` 门槛，见第 8 节。

### 2.2 三组正式实验的区别

| 实验 | Critic | Actor 使用的奖励 | Warmup 起点 |
|---|---|---|---|
| baseline | 单头，原 BT loss | 对抗分数 adv | 初始学生 + 共同单头初始化 |
| naive-rubric | 四头，BT + c/p/e 辅助损失 | 仍只使用 adv | 初始学生 + 由共同单头扩出的四头 |
| actor-rubric | 与 naive 相同 | adv 与 Critic 预测的 rubric 分数组合 | **复用 naive 对应的新 rubric Warmup** |

naive 的辅助损失会改变共享 Critic 主干，因此即便 Actor 只读 adv，也可能受到间接影响。Actor-rubric 则进一步显式读取 rubric 头的预测。

“Actor 只用 c”不等于历史的“correctness-only Critic”：前者仍让 Critic 学完整 c/p/e，只把 Actor 奖励中的 p/e 权重设为 0；后者只给 Critic 正确率监督，不需要过程 Judge。不要把两种消融混用。

### 2.3 三个 rubric 标签

| 维度 | 来源 | 含义与方向 |
|---|---|---|
| c：answer_correctness | `scoring/math.py` | 正确 1，明确错误或无答案 0；无法判定则 mask |
| p：verified_progress | Judge | 0 无实质进展，0.5 有独立正确中间结果，1 可见解答充分解决问题 |
| e：unresolved_error_severity | Judge | 0 未发现明确未解决错误，0.5 局部错误，1 关键路线或结论错误 |

p/e 可以为 `null`，含义是“不能可靠判断”，对应 mask=0，不是标签 0。e 越大越坏；训练 e 头时仍使用原标签，只有进入 Actor 奖励时才取负号。

Teacher 和 Student 都需要按内容评判，不能因为 Teacher 身份直接令 c=1。截断回答只评估已经可见的内容：未完成不自动等于过程出错，也不能因为最终答案错就断言所有中间推导都错。

### 2.4 当前 Judge 的简化流程

采用固定 rubric、`direct_v1` 协议：

1. 题目、**一条**回答、参考答案及可见性信息构成一次输入；不是把 Teacher+Student 的两条长轨迹拼成一次对比。
2. 本地 scorer 单独计算 c。
3. 过程抽样器选择需要标注的去重回答身份。当前 n4 配方每个全局逻辑 minibatch 最多选择 32 个身份，Teacher 和 Student 共用名额。
4. Qwen3-8B thinking Judge 输出两个字段的结构化 JSON：`verified_progress`、`unresolved_error_severity`，各自为 0、0.5、1 或 null。
5. 解析并写入标签及 mask，进入 Critic 辅助损失；缓存用于避免重复标注。

不要求长篇证据输出，不运行旧的语义复核链，不生成演化 rubric。标签仍是模型判断，不应称为经过独立数学证明的真值。

过程配额 32 不是“每步必定 32 个新请求”：缓存、去重和失败重试会影响实际调用数。也不表示全部学生都得到过程标签。全局题目 batch=64、n=4 时有 256 条学生回答，p/e 只覆盖其中一部分；c 不受过程名额限制。

源机配置中 Judge 上下文为 32768、输出预算为 8192，输出预算包含 thinking 开销；这和 Student 的回答上限 8192 是不同预算。部署先保留方法预算，不为了共卡静默裁短 Judge 输入或更改思考模式。

现有服务失败与连续无有效学生过程标签的保护继续保留，不能服务一直失败却悄悄退化为 correctness-only。

### 2.5 Critic 的损失怎么相加

设 Teacher/Student 的 adv 分别为 a_T、a_S，原 BT 损失为：

```text
L_BT = mean[-log sigmoid(a_T - a_S)]
```

它仍然按照 Teacher/Student 身份比较，不因答案对错交换 BT 的正负样本。rubric 为它增加内容监督，不重写 BT。

四头 Critic 在回答最后有效 token 输出 `[adv, z_c, z_p, z_e]`。后三个是 logits，辅助损失使用 `BCEWithLogits`，支持 0.5 软标签。

当前 `fixed_dimension_gated` 的口径：

```text
N_d = sum_i(w_i * mask_i,d)
gate_d = min(N_d / 4, 1)
L_d = sum_i[w_i * mask_i,d * BCEWithLogits(z_i,d, y_i,d)] / max(N_d, 1)
L_aux = (gate_c * L_c + gate_p * L_p + gate_e * L_e) / 3
L_critic = L_BT + 0.1 * L_aux
```

这里 w_i 是去重权重，避免 n=4 时重复出现的同一 Teacher 回答被额外放大；N_d 按**全局逻辑 minibatch**计算，包含 Teacher 和 Student。不同 GPU 或梯度累积微批不能各自重新归一化后随意相加。

有效标签很少时 gate 会降低该维贡献。缺失维度仍保留固定的除以 3，不能把它的权重重新全部分给 c。BCE 是“预测与目标相差多大”，越小越好，因此与 BT 相加是正确的，不需要因为 p 越大越好而将其损失取负。

这是**回答级的过程信息辅助监督**，不是对每一个推理步骤逐 token 打 PRM 标签。

### 2.6 Actor 如何读取 rubric

naive：`reward_source=adv_only`，额外开启影子记录，用于事后分析加入 rubric 会怎样改变排序，但不改变实际 Actor 奖励。

当前 n4 Actor 方案：`adv_plus_rubric_groupnorm`。令 c_hat、p_hat、e_hat 为 Critic 对应 logits 的 sigmoid：

```text
r = w_c * c_hat + w_p * p_hat - w_e * e_hat
s = (adv - 同题均值) / (同题 std(adv) + 1e-6)
    + w * (r - 同题均值) / max(同题 std(r), tau)
```

随后交给原 GRPO 再计算组内优势，原策略裁剪和 KL loss 保留。groupnorm 的 reward 内不再加入 KL，不代表取消 Actor 的 KL loss；源配置 KL loss 系数为 0.001。

- 先收齐同一题的 n=4 回答，在 driver 上按完整组计算，不能因为变成单卡或改 microbatch 而拆组。
- 使用本步 Critic **更新前、同一次四头前向**的预测；不是直接把 Judge 标签发给 Actor。
- w=0 或 rubric 在该组为常数时旁路回原 adv，避免除以 0 或制造虚假差异。
- 三组统一 `actor_reward.fp32=true`；只是奖励计算使用 FP32，不是将所有模型改成 FP32。
- n4 的组内标准化方案与旧 n2 的 `adv + beta*(c+p-e)` 不同，不要混用参数名和数值。

### 2.7 Replay buffer 的位置与限制

仓库保留 Teacher/Student 历史回答对池、淘汰、抽样和恢复逻辑。它是给 Critic 重放过去的回答对，Actor 仍使用本轮 fresh rollout。标签缓存只是复用标注结果，和 replay 改变训练样本不是一回事。

历史默认值包括容量 1024 对、最大年龄 8 step、512 MiB 序列化预算、混入比例 0.25、seed43。重放替换部分 Critic 批次，不是无限增加批量。

**当前正式 direct_v1 配方要求 `replay.enabled=false`，代码明确拒绝 direct_v1 与 replay 同开。** 本轮三组保持关闭。保留历史实现不代表已经支持当前协议；后续若研究 replay，需单独适配、验证，而不是在 H200 部署时顺手放开。

## 6. 第三步：实现 H200 共卡和建立新配置

### 6.1 共卡需要修改的地方

发布基线里至少有三处禁止 Judge 与训练 GPU 重叠：

| 文件 | 当前限制 | 最小修改方向 |
|---|---|---|
| `gad/tools/extension_config.py` | 配置校验要求两组 GPU 不重叠 | 增加默认关闭的显式共卡选项 |
| `gad/tools/rubric_judge.py` | 启动时拒绝重叠 | 只在同一显式选项开启时允许 |
| `gad/tools/preflight.py` | 已运行 Judge 的 health GPU 与训练重叠会失败 | 共卡模式下允许预期重叠，仍验证声明 GPU 与服务实际 GPU 一致 |

建议选项命名为 `resources.allow_judge_gpu_sharing`，**此名称是本交接文档提出的待实现接口，不是当前已有参数**。沿用现有配置系统登记默认值和布尔校验；新 H200 rubric 配置显式为 true，原多卡配置保持 false。

这项代码改动补三个定向 CPU 检查即可：默认仍拒绝重叠、显式开启允许声明的重叠、实际 GPU 或服务模型/协议身份不匹配仍拒绝。随后由真实共卡短测覆盖显存与运行行为，不为一个开关重跑全套测试。

同时核对 Judge 启动的忙卡检查：当前已有显存占用阈值检查。推荐顺序是空闲卡上先启动 Judge、health 通过后再启动训练；不应为了共卡把“杀掉占用者”变成自动流程。若仍被非训练进程的小额显存占用阻挡，报告实际原因再最小调整，不无条件取消所有占用检查。

Ray 只声明真实的 1 张训练 GPU，外部 Judge 不注册成第二张卡，不设置虚假的 `n_gpus_per_node=2`。检查 CUDA_VISIBLE_DEVICES 的物理/逻辑编号映射，训练和 Judge 都指向用户分配的同一张卡。

**只放开重叠检查还不够。** Judge 和 rollout 各自有 KV cache、模型和运行开销，还要为 Actor/Critic/reference、梯度、优化器、CUDA Graph 留空间。旧配置 Judge=0.85、rollout=0.55 是分卡设置，不能原样同开。比例相加小于 1 也不是实际无 OOM 的证明，应记录共卡峰值和实际可用 KV 容量。

### 6.2 不要继承错误的默认配方

以下文件保留历史用途，不能直接作为 H200 正式命令：

- `configs/launch_*n4*.yaml`：保留旧 Warmup 路径、四训练卡/两 Judge 卡；需要新建配置。
- `configs/methods/rubric_joint.yaml`：仍为旧 v27 prompt/spec、semantic_check=true，不代表当前 direct 方法。
- `configs/overrides/rubric_direct_v1.yaml`：是早期候选片段，配额还是 16；单独应用不足以还原当前正式 n4 配方。
- `train.yaml`：Judge 的默认 thinking、预算、prompt 也不是当前 direct n4 的完整设置。

最简单的实现可以是：从已验证 n4 launch 复制出新 H200 baseline/naive/Actor 三份独立配置，修改新机资源和来源；也可以用已有 method + machine + override 机制组织。二者选一种，不同时维护两套等价入口，更不要为此新增继承机制。

本文后续命令约定 Agent 创建：

```text

configs/h200_naive_n4.yaml
configs/h200_actor_n4.yaml
```

这些文件**当前尚不存在**。先创建并核对解析结果，再执行本文中引用它们的命令。位于 `configs/` 的文件引用项目根资产时写 `../assets/...`、`../data/...`；位于 `configs/machines/` 时写 `../../...`。不要把所有相对路径误当成相对于启动目录。

| 项目 | 新机口径 |

baseline、naive 从头开始：清空 `budget.init_from_warmup_run`、`budget.init_step`、旧 `budget.handoff_step`；不要只改 run_id 却还加载旧 checkpoint。保留 SeqKD 2 epoch、Warmup 1 epoch、GAD 新增 271 step。

17,405/64 按 drop_last 得每 epoch 271 步，因此期望 SeqKD=542、Warmup=271、GAD 从271到542。`budget.stage_epochs.gad=2` 是包含 Warmup 的**全局目标**，不是新增两个 epoch；优先显式写 `budget.gad_new_steps=271`。以 dry-run 和实际读取的数据行数为准。

不要为显存把 global batch 从64悄悄降成别的数。先调整 microbatch/动态 token 限额和梯度累积。选参脚本目前也写死了272–542的覆盖要求；改变训练预算会影响整个比较口径。

### 6.5 显存与速度参数的调整边界

先保留原 n4 方法及更新量，调整执行参数：

- Actor/Critic 参数与 optimizer offload 可以以关闭为候选；reference offload 独立处理，不因0.6B就保证所有常驻一定合适。
- gradient checkpointing 先保留，以长回答共卡峰值为依据再考虑关闭。
- Critic microbatch=2 是源机起点；单卡先测能否运行，之后再尝试4等候选。
- rollout max_num_seqs、KV预算、动态 token 限额可调；单卡不用继承多卡吞吐假设。
- Judge 并发8、配额32先保留方法；必要时先调并发，而不是降低标注配额来混淆方法和加速。
- 正式三组尽量使用同一套 Actor/Critic 执行参数。只有 rubric 组需要 Judge；运行成本分别记录，不宣称基线也有同样 Judge 开销。

提速只做短而有信息量的比较：区分启动/图捕获、生成、标注等待、训练、保存；同时记录生成 token 数。单步总时间受回答长度影响，不用一次更短的生成声称整轮倍数加速。

## 8. 第五步：短程验证怎么做才够用

### 8.1 验证目标与预算

短测不是模型效果实验，而是确认：真实权重加载、Actor/Critic 真更新、Judge 共卡、Warmup→GAD、checkpoint 保存恢复都能正常工作。

先用小 batch/短输出做便宜的逻辑验证；随后至少做一次**正式 batch=64、n=4、8192上限、共卡**的实际 GAD 更新，观察峰值。短输出跑通不能声称长输出配置不会 OOM；若样本普遍很短，也要明确长回答峰值尚未覆盖。

短测必须放独立 `h200_smoke_*` run。允许短测专用关闭完整验证、缩小样本数、降低前期 Critic 门槛，正式配置不得继承这些变化。

| 短测 | 最低应证明的内容 |
|---|---|
| SeqKD | 1–2次真实参数更新、保存，Teacher数据可用 |
| baseline Warmup→GAD | 单头训练、两个阶段正确交接、GAD Actor更新 |
| rubric Warmup→GAD | 四头由共同单头派生；Warmup期间已有有效c/p/e；Judge共卡可用 |
| GAD 保存恢复 | 在阶段中间正常停一次，恢复至下一个global step，数据游标与扩展状态加载 |
| Actor混合奖励 | 使用工程占位参数跑1步，证明groupnorm通路有效，不视作正式选参 |
| 小规模外部评测 | 已导出模型完成少量题目，确认评分器与8任务路径可用 |

默认 `optim.critic_warmup=10` 会让特别短的 SeqKD/Warmup 测试看不到 Actor 更新。工程测试可显式设0并记录；GAD 构建的 trainer 已设 critic_warmup=0。不要只看到进程退出就写“Actor 更新验证通过”。

### 8.2 可用的短程交接与恢复命令

以下需要先创建可运行的 `configs/h200_naive_n4.yaml` 并启动相同配置的 Judge。示例保留正式 batch/长度，若首轮只需廉价逻辑测试，可另建 smoke 配置降低这些项，再回到正式形状做一次确认。

第一步：建立新的短 Warmup，显式规定 GAD 新增3步：

```bash
bash scripts/train.sh --config configs/h200_naive_n4.yaml \
  --run-id h200_smoke_naive --stages warmup \
  --warmup-smoke-steps 2 --gad-new-steps 3 \
  --set optim.critic_warmup=0 \
  --set resources.save_freq=1 \
  --set run.disable_validation=true
```

第二步：从其完成的 Warmup 进入 GAD，只执行1个新增step并正常保存：

```bash
bash scripts/train.sh --run runs/h200_smoke_naive \
  --stages gad --resume --max-stage-steps 1
```

第三步：解除单次调用限制，继续到原定目标：

```bash
bash scripts/train.sh --run runs/h200_smoke_naive \
  --stages gad --resume --set run.max_stage_steps=null
```

期望 Warmup结束step2，GAD第一次到step3，恢复后到step5；第二步是“本次调用达到限制”，不能被标成整个GAD完成。查看实际manifest、日志和参数更新证据。

不要一开始对 `--stages warmup,gad` 同时使用 `--max-stage-steps 1` 来期待自动交接：Warmup被中断后pipeline会停止，尚未完成的Warmup不能进入GAD。

baseline采用相同三步模式、改用baseline配置与独立run_id，不启动Judge。SeqKD可以单独执行：

```bash
bash scripts/train.sh --config configs/h200_baseline_n4.yaml \
  --run-id h200_smoke_seqkd --stages seqkd \
  --set budget.stage_epochs.seqkd=null --set budget.seqkd_steps=2 \
  --set run.engineering_smoke=true --set optim.critic_warmup=0 \
  --set resources.save_freq=1 --set run.disable_validation=true
```

不要为短测改正式run的预算。上面的廉价检查关闭了训练内验证，因此还需用少量dev样本完成一次**启用数学评分的训练内验证**，确认指标写出和不阻断交接的行为；不能全部关闭验证后就声称评估链路已经通过。使用独立smoke配置，正式quick128/full512保持原样。

Actor工程验证从完成的rubric smoke Warmup另起GAD，明确 `engineering_smoke=true` 和单次步数限制，使用占位w/tau验证代码通路；不将 `actor_reward_selection_confirmed=true` 当作绕过正式选参的捷径。

### 8.3 应记录什么

- 每个阶段实际开始/结束step、初始化checkpoint来源、恢复的checkpoint路径。
- Actor/Critic更新是否发生，loss与梯度是否有限，四头是否按预期存在。
- c/p/e有效标签数量、null与失败原因、请求数/缓存命中/耗时，不能只报Judge服务存活。
- 恢复后扩展统计、数据位置、Judge账本与缓存没有被误作新run；没有重复提交已完成step。
- 共卡显存峰值、回答token数、生成/标注等待/训练/保存时间。保存步骤与普通步骤分开看。
- 若有小问题，修对应代码并只重测受影响路径；不借部署全面重构验证或恢复框架。

## 9. 后续正式实验安排

### 9.1 实验树

```text
初始 Qwen3-0.6B
  ├─ 公共 SeqKD（2 epoch）
  ├─ baseline Warmup（1 epoch） → baseline GAD（新增271步）
  └─ rubric Warmup（1 epoch）
       ├─ naive GAD（新增271步，记录影子奖励）
       └─ Actor-rubric GAD（另起run，新增271步，新naive选参后运行）
```

不要多跑三份相同SeqKD，也不要为Actor再训练一份不同rubric Warmup。baseline与rubric Warmup独立训练，但共享初始学生与共同adv初始化来源。

### 9.2 推荐 run 命名与正式命令形状

使用新名字，不覆盖旧机同名实验。下面以三份待创建并验证的H200配置为前提。

先运行公共SeqKD和baseline完整流程，此时Judge不必运行：

```bash
bash scripts/train.sh --config configs/h200_baseline_n4.yaml \
  --run-id h200_baseline_06b_17k_n4 --stages seqkd,warmup,gad
```

再启动Judge、确认health，运行rubric Warmup和naive GAD：

```bash
bash scripts/rubric_judge.sh --config configs/h200_naive_n4.yaml --action start
bash scripts/rubric_judge.sh --config configs/h200_naive_n4.yaml --action health
bash scripts/train.sh --config configs/h200_naive_n4.yaml \
  --run-id h200_naive_06b_17k_n4 --stages warmup,gad
```

这些命令以前台形式展示。正式长任务用用户已有tmux或后台日志方式托管；不要因为关闭VS Code造成中断。Agent应给出最终实际命令及日志位置，不另开发任务管理服务。

### 9.3 naive完成后选Actor参数

```bash
python gad/tools/select_actor_reward.py \
  --run runs/h200_naive_06b_17k_n4 \
  --output reports/h200_actor_selection
```

工具要求完整step272–542影子日志和最终step542 checkpoint；它针对目前确定的预算，不支持任意训练长度。按题目稳定划分选择集/复核集，比较full与c-only以及w=0.25/0.5/1/2，tau来自选择集组内标准差的25分位，零值与中位数仅作敏感性分析。

旧机唯一通过的候选是 **Actor-c-only、w=0.25、tau=0.045992180705070496**。这是旧机反事实分析结果，不保证新机最佳，也不证明Actor最终提升；新机重新选参。若没有候选通过，不临时放松条件或悄悄扩大权重，应报告结果并由用户决定后续研究设置。

选参结果经用户确认后，把分量/w/tau写入Actor配置并置 `rubric.actor_reward_selection_confirmed=true`。这是当前正式Actor路径已有的科学选择要求，不新增其他审批流程。

Actor必须指向**新rubric Warmup**，而不是naive最终GAD：

```bash
bash scripts/train.sh --config configs/h200_actor_n4.yaml \
  --run-id h200_actor_06b_17k_n4 --stages gad \
  --init-from-warmup-run runs/h200_naive_06b_17k_n4 \
  --init-step 271 --gad-new-steps 271
```

正式执行前dry-run确认只读取该run的Warmup271。显式Warmup初始化只适用于 `--stages gad`，不能再同时请求seqkd,warmup。

### 9.4 对照实验应报告什么

首先比较新机SeqKD、baseline、naive、Actor四个最终模型。旧3090结果是历史参考，不能和H200新配方直接混成同一严格对照。

除八任务整体得分外，报告回答长度、截断率、正常结束条件下正确率、训练耗时及Judge开销。正常结束条件下正确率只是条件统计，不能单独代替总体效果；小规模AIME差异避免过度解释。

Actor尤其报告奖励干预比例、排序净修正/损坏、正确与错误回答的优势差，以及后期是否漂移。不要仅凭“翻转更多”得出更有效的结论。

## 10. 八任务16k评测

统一任务和采样次数：

| 任务 | 每题采样n |
|---|---:|
| AIME24 | 8 |
| AIME25 | 8 |
| AMC23 | 8 |
| MATH-500 | 2 |
| Minerva | 4 |
| Olympiad-Bench | 2 |
| GPQA | 8 |
| MMLU-Pro-Math | 2 |

输出上限16384，总上下文18432，seed42，non-thinking，temperature=1.0、top_p=0.95。不要额外加AMC24变成九任务，也不要把所有任务统一n=8后和旧表直接比较。

原四项由 `scripts/eval.sh` 默认选择，新增四项由 `evaluate/run_extended_eval.sh` 提供路径与task-n。最少改动的做法是分两次运行，再合并报告；不需要新写八任务评估器。

先停止Judge，确保训练已经释放GPU。以baseline run为例：

```bash
bash scripts/eval.sh --run runs/h200_baseline_06b_17k_n4 \
  --methods base,seqkd,gad --gpu-ids 0 \
  --profile core4_h200_taskn_16k \
  --max-tokens 16384 --max-model-len 18432 --dry-run

bash evaluate/run_extended_eval.sh --run runs/h200_baseline_06b_17k_n4 \
  --methods base,seqkd,gad --gpu-ids 0 \
  --profile ext4_h200_taskn_16k \
  --max-tokens 16384 --max-model-len 18432 --dry-run
```

确认后去掉dry-run执行。naive/Actor run通常只需 `--methods gad`；它们没有独立SeqKD产物，不要套 `base,seqkd,gad` 导致找不到阶段。base与公共SeqKD只评一次即可。

新run、新profile且scorer一致时，不需要习惯性添加 `--allow-new-eval-scorer --generate-missing`。只有明确做跨评分器的旧结果重评分/补生成时才使用相应参数，不把它们当通用忽略错误开关。

数学统一走当前scorer；选择题与Minerva/Olympiad的评测专用规则保留在evaluate内。ROUGE-L不是数学正确率，也不进入rubric损失。launch里旧的 `eval.*` 列表和8192不是本节八任务16k协议；本轮先显式评估，暂不依赖训练后自动评估的旧默认值。

## 11. 常见故障与处理边界

| 现象 | 先检查什么 |
|---|---|
| 找不到训练数据 | 是否误选 `dapo_math_17k` 而不是 `_v2`；归档是否多解一层LMOps |
| import了错误verl | 是否pip装了别的verl；阶段PYTHONPATH是否来自固定worktree |
| scorer/Judge身份不匹配 | 是否用了旧run/旧fingerprint；服务是否按当前prompt/spec/模型启动；不要先取消校验 |
| Judge GPU overlap | 共卡选项是否在配置校验、启动器、preflight三处同时生效 |
| Judge启动通过但训练OOM | 分卡显存比例是否照搬；Judge/KV/训练/Graph是否共同超预算 |
| Warmup两步“通过”但Actor没更新 | critic_warmup门槛与实际参数更新证据 |
| GAD重启从头读数据 | 是否用 `--run ... --resume`；保存状态与数据游标是否存在 |
| naive缺少p/e标签 | 配额、mask、服务失败、缓存/请求统计；不能把null当0填补 |
| stage完成后没有自动接续 | 实际完成标记与checkpoint、是否只是单次调用限步；不把未决数学评分当训练失败 |
| 试图开启direct+replay报错 | 当前明确不支持，属于后续方法工作，不是单卡部署bug |
| 小batch很快，正式训练很慢 | 长度/token数、Judge等待和保存时间；不要只比较表面step秒数 |

同一阶段恢复与Warmup→GAD交接不同：交接从Warmup权重建立GAD起点，GAD优化器按阶段逻辑初始化；GAD中断恢复则恢复该阶段optimizer/scheduler/RNG及扩展状态。不要混成“只加载Actor权重即可续训”。
