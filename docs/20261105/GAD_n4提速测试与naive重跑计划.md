# GAD n=4 提速测试与 naive 重跑计划

状态：2026-11-10 用户已授权执行至阶段 3，功能验证已完成，显存各阶段在续训步补测；首两步连续显存采样仍有缺口，详见报告。结果见 [执行报告](../../reports/gad_speed_20261110/README.md)。本文只规定提速测试、代码改动、验证和运行顺序；停止当前 naive、启动正式训练和正式评测均由用户执行，执行模型只做经用户同意的短测（每次不超过 3 步、独立 run id）。本文是 [GAD n=4 三组对照实施方案](GAD_n4三组对照实施方案.md) 的补充，三组的方法定义、评测协议和第 3 组选参规则不变。

硬约束：

- **GPU 0、5 不可用**（容易崩）。所有测试只用训练卡 1–4 和 Judge 卡 6–7，因此任何 GPU 测试都要求当前 naive 已停止或已结束。
- **replay 必须保留**，是下一步实验要引入的功能。它不进入任何清理清单，本文所有代码改动都要保证 replay 路径的测试继续通过（第 5.5 节）。
- 提速改动只允许改"在哪里算、什么时候算"，不允许改标签、奖励、损失和采样分布。会改变这些的做法一律放到下个系列（第 8 节）。

当前 naive（`rubric_naive_n4_06b_17k_v1`）11 月 10 日 10:40 启动，到 11:37 只完成 272、273 两步。

### 1.2 rollout 被 KV 缓存容量卡住

- 本次 naive 的 preflight 记录（`runs/rubric_naive_n4_06b_17k_v1/reports/preflight_*.json`）：`gpu_memory_utilization=0.55` 时 KV 池 8.857 GiB，按 114,688 字节/token 折合约 8.3 万 token，只够约 10 条满长序列。
- baseline n=4 每卡 64 条回答，平均每步每卡需要 37.3 万 token，是 KV 容量的 4.5 倍。
- 佐证：n=2（每卡 32 条）的 `rubric_direct_06b_17k_20261026`、`rubric_actor_06b_17k_v1` 和 n=4（每卡 64 条）的 baseline，单卡吞吐都是约 1020~1045 token/秒。并发加倍，吞吐没有变化。
- 利用率只能给到 0.55 的原因：actor、critic、ref 的参数和优化器 offload 全部关闭（`configs/machines/3090_4gpu.yaml`），训练状态常驻约 10 GB/卡，加上 vLLM 的 12.96 GiB 预算正好是实测峰值 23.5 GiB。
- 历史短测 `runs/performance_benchmarks/formal17k_baseline_20261020`（全部 offload，单步 429 秒）与 `formal17k_resident_20261020`（常驻，单步 438~464 秒）在同一 KV 设置下没有显示 offload 更慢。两者都只有 1~3 步，只能说明搬运开销不大，不能说明更快。
- "offload 加更大 KV 池"这一组合此前没有测过。

### 1.3 Judge 标注的等待方式

- 标注在 `update_critic` 内同步进行，期间 4 张训练卡空转；rollout 的约 500 秒内 Judge 卡空转。
- 每步 32 个名额中 11 个是 Teacher。Teacher 的入选只由种子、阶段、步数和题目决定（`gad/extensions/process_sampling.py` 第 40–45 行），与学生输出无关，rollout 开始前就能确定。
- 单请求速度约 19 token/秒；输出平均约 1,350 token，几乎全是思考；p99 约 5,900 token，单条约 5 分钟。整批耗时同时受"总量/并发"和"最长单条"两个下界约束。
- 客户端并发 8，服务端 `--max-num-seqs 16`（`gad/tools/rubric_judge.py` 第 82 行）。并发不进入 Judge 指纹（`extension_config.service_identity`），调并发不改变标签缓存的键。

### 1.4 续训会换数据顺序

已复现：`data.pt` 只保存 `samples_yielded`，没有保存采样器的生成器状态，续训后的题目序列与不中断时不同（step 274 与正式 baseline n=4 重合 0/64）。上一轮续训验证只核对了游标。考虑到本机有不稳定因素，长跑前必须修复。

## 2. 两种推进方式与建议

| | 方案甲：等本轮 naive 跑完 | 方案乙：现在停 naive，先测再重跑 |
|---|---|---|
| 当前 naive | 继续，约还需 96 小时 | 停止，已完成的 2 步（约 1 小时）作废 |
| 提速受益范围 | 只有第 3 组及以后 | 第 2、3 组及以后 |
| 第 2、3 组后端是否一致 | 不一致（第 3 组多了提速和续训修复） | 一致 |
| 续训修复 | naive 这 96 小时内若崩溃，只能从 271 重来或接受换序 | 重跑前已修复 |
| 代价 | naive 多花的时间（推算 20~35 小时以上） | 测试和改代码期间训练卡空闲 |

**建议方案乙。**理由：已投入只有 2 步；等得越久作废的越多；两组 rubric run 用同一后端，对照更干净；续训修复在长跑之前落地。

方案乙的止损规则：第 4 节的测试没有达到采纳门槛的改动一律不采纳，重跑时保持现设置；第 5 节的代码改动若在用户给定的时限内没有通过第 6 节验证，则只带已验证的部分重跑，其余放到下个系列，不在第 2、3 组之间新增。

以下各节按方案乙编写。若选方案甲，第 3~6 节整体顺延到 naive 结束后执行，第 3 组带上已验证的改动，并在报告中注明第 2、3 组执行设置不同。

## 4. 阶段 1：只改配置的短测

产物统一放在 `reports/gad_speed_20261110/`，短测 run id 以 `speed_` 开头，写入独立目录，不触碰任何正式 run。

### 4.1 A1：offload 加更大的 KV 池

目的：验证 rollout 是否受 KV 容量限制，并选定利用率。

做法：沿用 `reports/gad_n4_20261105/baseline_smoke.yaml` 的短测方式（baseline 配置，从 `runs/baseline_06b_17k` 的 Warmup271 交接，`run.max_stage_steps: 2`），只覆盖下列键。baseline 配置不需要 Judge。

| 档 | offload（actor/critic 参数与优化器、ref 参数） | `rollout.gpu_memory_utilization` | KV 池（按 preflight 算式） | 相对现状 |
|---|---|---|---|---|
| K0 现状 | 全关 | 0.55 | 8.86 GiB，约 8.3 万 token | 1.00 |
| K1 | 全开 | 0.75 | 13.57 GiB，约 12.7 万 token | 1.53 |
| K2 | 全开 | 0.85 | 15.93 GiB，约 14.9 万 token | 1.80 |
| K3 | 全开 | 0.90 | 17.10 GiB，约 16.0 万 token | 1.93 |

顺序：先跑 K2。K2 若 OOM 则跑 K1；K2 通过则再跑 K3。K0 的对照先用正式 baseline n=4 的 step 272、273 记录（同一 checkpoint、同一批题、同样的种子）；若最优档相对该记录的单步降幅不到 15%，同日补跑 K0，排除机器负载差异。

每档记录：`timing_s/generate_sequences`、`timing_s/gen`、`old_log_prob`、`ref`、`reward`、`update_critic`、`update_actor`、`step`，单卡吞吐，每 3 秒采样的各卡显存峰值，是否 OOM。offload 的搬运开销会体现在 `gen` 与 `generate_sequences` 的差值以及各更新环节里，要分开看。

采纳门槛：两步都没有 OOM（step 272 就包含 Actor 更新），且单步总耗时比对照下降至少 10%。多档通过时取最快；差距在 5% 以内时取利用率较低的一档，留显存余量。都不达标则保持 K0，并把"KV 受限"的判断记为未证实。

可选的后续一档（只在 K 档被采纳、且训练阶段显存峰值有 4 GiB 以上余量时做）：关闭 actor 和 critic 的梯度检查点。它在数学上等价，只看更新时间和峰值显存；采纳门槛同上。

预计占用：每档约 35 分钟，共约 2~2.5 小时。

### 4.2 A2：Judge 并发 8 对 16

目的：确认并发 16 的整批耗时、显存和解析成功率。

做法：沿用 `reports/judge_direct_v1_20261025` 固定 32 条输入的并发对照方式（命令见该目录 `commands.md`），Judge 仍在 6、7 卡，TP=2。同日先跑并发 8 作对照（历史记录 403.0 秒），再跑并发 16。不改服务端启动参数，不改 `judge_client.py` 和 `rubric_judge_server.py`（两者的哈希在 Judge 指纹里）。

记录：整批耗时、单请求耗时和每秒 token 的中位数与 P95、解析成功数、Judge 卡显存峰值、两档之间逐条标签是否一致（同种子，仅作参考，不作门槛）。

采纳门槛：无 OOM、解析成功数不低于并发 8、整批耗时下降至少 15%。

A2 与 A1 的计时测试不要同时跑，避免 CPU 争用影响读数。预计占用约 20 分钟。

## 5. 阶段 2：代码改动

所有改动通过后端补丁和扩展实现，生成新的后端哈希；已有后端目录不动。

### 5.1 B1：续训时恢复采样器状态（必须）

- 在 checkpoint 的 `data.pt` 中保存本 epoch 开始时的采样器生成器状态，续训时恢复后再按 `samples_yielded` 快进。只改续训路径，不中断时的题目顺序不变。
- 旧 checkpoint 没有这个字段。对它们续训时必须报错并给出说明，不允许静默退回旧行为。
- 验证以题目身份为准：续训后每一步的 `question_id` 集合必须与 `runs/baseline_n4_06b_17k_v1/gad/extension_metrics.jsonl` 中同一步的记录完全一致。

### 5.2 B2：Teacher 标注预取

- 每步开始、rollout 之前，按与 `select_process` 相同的规则算出本步入选的 Teacher（GAD 阶段 11 个），在后台线程发给 Judge，结果写入标签缓存。rollout 结束后主流程照常执行，这些 Teacher 命中缓存。
- 预取是尽力而为：预取失败、超时或键没对上时，主流程按原路径请求，结果不依赖预取是否成功。
- 预取的每次请求都要写入 `judge_attempts.jsonl`（带步数），并计入 `max_annotation_attempts`，保证标签来源记录完整。
- 缓存键必须与主流程逐位一致。验证标准：短测中 Teacher 预取命中 11/11；不足即视为实现错误。
- 启用 replay 时，Teacher 候选集合会包含回放样本。本轮 replay 关闭，预取只按当前批计算；replay 开启时未命中的部分自动走原路径。

### 5.3 B3：学生标注提前提交

- 把 `GadExtensions.prepare` 拆成两段：rollout 结束后立即抽取配对、做 replay 选择、选出标注对象并在后台提交 Judge 请求；原 `prepare` 的位置改为等待结果、打包 Critic 批和写监控。
- log-prob、ref、reward、优势计算在等待期间照常进行（约 85 秒）。等待结果发生在任何优化器更新之前，Judge 不可用时"本步不更新"的语义不变。
- replay 的 `select` 每步仍只调用一次，调用顺序相对其他随机数消耗不变。

### 5.4 B4：Actor 更新移到 Critic 更新之前（可选）

- Actor 更新只用已算好的优势，不依赖本步的 Critic 更新。调换顺序后，Actor 更新的约 115 秒也能和标注等待重叠。
- 风险点：调换后，Judge 失败时 Actor 已经更新。实施前要确认 `abort_step` 的实际行为是终止进程（未保存的内存状态随之丢弃，续训从上一个完整 checkpoint 开始）；如果是跳过本步继续训练，则 B4 不做。
- 还要确认 `prepare` 不会改动 Actor 更新读取的张量，以及 `commit` 的记录内容不受顺序影响。
- B4 独立于 B2、B3，可以单独放弃。

### 5.5 约束

- 不修改 `gad/extensions/judge_client.py`、`gad/tools/rubric_judge_server.py`、`rubric/core/semantic_v24.py`、`rubric/core/process_direct.py`、rubric 的 spec 和 prompt。它们的哈希在 Judge 指纹、协议身份或缓存键里，改了会让第 2 组的标签缓存对第 3 组失效。
- 第 2 组启动后到第 3 组结束前，扩展目录和补丁生成器冻结，保证两组后端哈希相同。
- replay 相关代码（`replay_buffer.py`、`runtime.py` 中的 select/commit、`replay.*` 配置、`test_replay.py`）保留，行为不变。
- CPU 测试：`bash gad/tests/run_all.sh` 全部通过，其中 `test_replay.py`、`test_resume_patch.py`、`test_algorithm_parity.py`、`test_process_sampling_direct.py` 必须在新后端上通过；B1–B4 各补充对应用例（B1 按题目身份断言，B4 断言调换顺序前后 Actor 损失与梯度、Critic 损失逐值相同）。

## 6. 阶段 3：合并后的 GPU 验证

用最终候选配置跑一次 naive 短测：从 `runs/rubric_direct_06b_17k_20261026` 的 Warmup271 交接，训练 2 步后停止，再续训 1 步（与上一轮"2+1"相同）。逐项核对：

1. **题目身份**：step 272、273 和续训后的 step 274，`question_id` 集合与正式 baseline n=4 同一步完全一致。
2. **奖励不变**：naive 的 `advantages_actual_max_error` 和 `advantages_change_mean` 均为 0。
3. **标注**：每步入选 32 个（Teacher 11、学生 21）；Teacher 预取命中 11/11；`judge_attempts.jsonl` 记录齐全；失败标注仍按无效屏蔽，不记为 0。
4. **分布对比（只报告，不作门槛）**：step 272 的截断率、平均长度、C/W/T 构成，与已有记录对比（baseline n=4 正式：截断率 0.738、平均 6,966 token；naive v1：截断率 0.734、平均 6,932 token）。采样带固定种子，预期接近；逐位不保证相同。
5. **显存**：rollout、Critic 更新、Actor 更新、保存 checkpoint 各阶段无 OOM，记录各卡峰值。
6. **耗时**：按第 1.1 节的口径列出各环节时间，与现状对比，给出 271 步的线性外推。
7. **后端**：新后端哈希已记录，旧后端目录和历史 run 未被修改。

任何一项不通过，对应改动撤回后重测；不为通过检查而放宽检查。

baseline n=4 不重跑。理由：采纳的改动都不改变标签、奖励、损失和采样分布；正式报告中注明 baseline 使用旧执行设置，并附本节第 4 项的对比。

## 7. 阶段 4–5：naive 重跑与后续

1. 用户确认最终配置后启动 `rubric_naive_n4_06b_17k_v2`，方法设置与原 naive 完全相同，只变执行设置和后端。
2. **50 步检查点**（step 321 之后，只读、仅 CPU）：在影子日志上重算
   - p/e 标签的覆盖率和取值分布，按 C/W/T 分开；
   - p̂、ê 在 W 内部与标签的相关（n=2 时为 0.05 和 0.09）；
   - 对抗分、ĉ、p̂、−ê 在 CW、CT、TW 配对上的排序正确率；
   - 全截断组、无正确回答组的占比，以及这些组里 rubric 分数的组内标准差。

   结果交用户决定第 3 组候选分量（完整三维、只用 c，或另行说明的组合）。这一步不改变 naive 的运行。
3. naive 跑完后按原方案第 6 节选参，用户确认后启动第 3 组。第 3 组启动前把 naive 的标签缓存复制到新 run 目录，Teacher 部分可直接命中；需先确认 preflight 允许非空缓存。
4. **评测窗口**：GPU 0、5 不可用，两个 Warmup271 和各 run step500 的评测只能排在卡 6–7 或 1–4 空闲、且没有计时测试的时段（例如阶段 2 改代码期间）。由用户启动。

## 8. 本轮不做、留给下个系列的事项

会改变结果的提速：

- 复读循环提前停。step542 开发集（贪心）上，57% 的截断回答以严格周期循环结尾，起点中位数约 3,300 token，推算可省约 23% 的 token。它会改变 Critic 看到的回答。
- 降低 `max_response_length`。不建议降到 4096：baseline n=4 中 26% 的正确回答超过 4096 token。
- Judge 思考预算、非思考 Judge、跳过低信息量的截断回答等协议层改动。
- 按步和题派生 rollout 种子。

框架清理（等三组全部结束后一次性做，届时提交并打 tag）：

## 9. 风险

- **A1 可能不成立。**KV 受限是由容量算式和"并发加倍吞吐不变"推断的，没有直接看到 vLLM 的排队状态。短测不达标就维持现状，损失约 2 小时。
- **offload 后的显存余量。**利用率提高后 rollout 阶段的余量变小，且 `enforce_eager=false` 时 CUDA graph 池在训练阶段常驻。短测只有 2 步，覆盖不到正式验证（step 400、542）和最长批次；正式 run 的前几步和第一次验证需要盯显存。
- **不保证逐位一致。**批内组成变化会带来 BF16 数值差异，个别采样 token 可能不同。这在不同 run 之间本来就存在，但意味着"执行设置不影响结果"只能在分布意义上成立。
- **B4 改变了失败时的状态。**见第 5.4 节，条件不满足就不做。
- **短测时间外推不准。**2~3 步的均值不能代表全程，回答长度随训练变化；外推只用于判断是否值得采纳。
