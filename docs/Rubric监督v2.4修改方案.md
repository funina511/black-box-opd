## 1. 修改目标与边界

当前 Naive Rubric 保留原 GAD 的 Teacher–Student BT Loss，使用独立 Judge 评估数学轨迹，并通过三个辅助 Head 训练 Critic。

现阶段的主要问题：

1. 严格的理由和证据要求导致部分正确标签被 Mask。
2. 放宽引用限制后，错误数学判断仍可能通过结构校验。
3. Judge 可能把自己完成的推导错误归属于待评估轨迹。
4. 部分标签有效率过低，使单个错误标签获得较大的辅助梯度权重。
5. 尚未证明 Process Rubric 相比 Correctness-only 的增量价值。

### 本轮保持不变

- 保留 `adv`、`answer_correctness`、`verified_progress`、`unresolved_error_severity` 四个 Critic 输出通道。
- 保留原始 BT Loss，不改变 Teacher–Student 偏好标签。
- Warmup 的 Actor 保留原始监督更新逻辑；GAD 的 Actor 保留基于 `adv` 的原始更新逻辑，不直接使用 Rubric Reward。
- Rubric 辅助损失从 Warmup 开始训练 Critic，并延续到 GAD；不将 Critic 预训练后冻结。
- 答案正确性继续由统一规则 Scorer 提供。
- 保留 0 / 0.5 / 1 / unknown 标签体系。
- 保留 Judge 独立运行及 Thinking 模式。
- 暂不引入动态 Rubric、Rubric Generator 或 Replay Buffer。

### 放宽的边界

本轮放宽的是证据的表达负担，不降低数学正确性和原文归属要求。Teacher 与 Student 适用相同标准；Judge 输入保持来源匿名，审计时再按来源分组。

| 允许放宽 | 必须保留的约束 |
|---|---|
| 简短理由、忠实转述，不要求逐字重抄公式 | 判断仍须由轨迹原文支持，不能依赖 Judge 补出的步骤 |
| 一个事件关联多个原文片段 | 这些片段确实共同支持该事件，不能仅因 ID 存在就算核验通过 |
| 只提供足以支持结论的关键证据 | 一个正确步骤只能支持相应的局部进展，不能证明整题完成 |
| 保留与失败事件独立的正确进展 | 关键错误、修复或依赖关系的不确定性仍需影响相关标签 |
| 不同记号、表达顺序和合法解法 | 数学含义与适用条件不能改变 |

“可靠但几乎全部相同”的标签也可能缺少训练价值。因此既要减少误标，也要检查保留下来的标签是否能区分过程质量；不通过强行平衡分数分布制造区分力。

## 2. P0：建立标签质量基线

**目的：先明确有效监督为何丢失、错误监督为何被接受。**

在修改 Prompt 和 Parser 前，先固定并审查现有数据。

### 2.1 审查现有失败样本

优先检查已完成的 8 条 V2.3 输出，以及此前发现的典型问题：

- Judge 自己算出正确答案，却将其归属于 Student。
- 原文没有修复，但 Judge 声称错误已经修复。
- 正确但未完成的推理前缀被整体 Mask。
- 合法的不同解法或未展开分支被误认为错误。
- 只有计划性描述，却被判为实质进展。
- 已发生的关键错误被误判为局部错误。

针对每个样本记录：

| 字段 | 含义 |
|---|---|
| `raw_score` | Judge 原始分数 |
| `final_score` | Parser 处理后实际使用的分数 |
| `mask_reason` | Mask 原因 |
| `score_valid` | 经审查后，数学分数是否正确；未审查填 pending |
| `evidence_valid` | 经审查后，所选原文是否支持判断；与分数正确性分开记录 |
| `error_type` | 数学错误、证据归属、修复关联、结构错误等 |
| `review_source` / `review_status` | 人工审查、定向二次核查或仅结构检查，以及待审、通过、失败、分歧状态 |

需要区分两种情况：

- 正确分数被错误 Mask：损失了有效监督。
- 错误分数通过验证：引入了监督污染。

还需单列“分数碰巧正确，但所给证据不支持判断”的情况。这类结果不能作为已经核验可靠的标签统计。由模型辅助审查的结果须标明来源，不能写成人工审查完成。

### 2.2 建立小规模人工审查集

先审查现有冻结的 24 条样本中已经生成的结果，未完成项明确标记。该集合已经多次用于调整协议，应作为开发诊断集，不能继续当作未经调参影响的独立验收集。

在查看新结果或继续调整 Prompt 前，从已有真实 Teacher/Student 轨迹中另行固定一份未用于调参的留出集合，覆盖简单、复杂、正确、错误和截断回答。记录样本 ID、问题 ID、抽样方式及哈希，避免同题近重复泄漏；不从正式评估测试集选样本。留出集一旦用于修改规则，就应改记为开发集，不能仍宣称独立验收。

开发集与留出集分别报告；困难反例用于检查已知失败模式，真实分布样本用于估计实际表现，不能混在一起计算一个总体准确率。默认复用已有轨迹，不额外启动 Actor 采样。新增 Judge 请求和审查规模遵守第 7 节预算。

验收前写清各维允许的误标风险、关键错误的判定标准和样本量。报告实际分子/分母及样本不足的限制，不根据少数案例声称达到高准确率，也不看到结果后再降低验收标准。

**阶段产出：** 一份标签质量审计报告，为 V2.4 的修改提供对照基线。

## 3. P1：调整过程维度的判定和证据要求

### 3.1 Answer Correctness：不修改

继续使用统一规则 Scorer。

不让 Judge 根据过程推理自行覆盖规则 Scorer 的最终答案标签。

### 3.2 Verified Progress：放宽证据形式，保持数学正确性要求

| 分值 | 判据 |
|---|---|
| 0 | 经过充分检查，没有相关的实质进展 |
| 0.5 | 存在至少一个独立正确、与目标相关的有效中间结论 |
| 1 | 可见推导充分解决题目 |
| unknown | 无法可靠判断 |

**重点修改：**

- 对 `progress=0.5`，只要求存在足以支持部分进展的正确原文证据，不强制 Judge 证明整条推理都正确。
- 允许正确的可见前缀贡献部分进展，即使回答最终截断或没有正确最终答案。
- 不强制 Judge 引用每一个正确步骤；允许只提供关键的支持证据。
- Judge 自行补出的正确结论不能算作待评估轨迹已经取得的进展。
- 单纯重述问题、提出解题计划或沿错误前提继续计算，不自动构成可靠进展。
- `progress=1` 仍要求充分的整体证据，不能因发现一个正确步骤就直接判满分。

### 3.3 Unresolved Error Severity：采用非对称验证

| 分值 | 判据 |
|---|---|
| 0 | 已充分审查可见数学内容，没有未修复错误 |
| 0.5 | 存在局部错误，但没有破坏核心路线 |
| 1 | 存在尚未修复、影响关键路线或结论的错误 |
| unknown | 无法可靠判断 |

**重点修改：**

- 对明确存在的错误，优先使用局部原文证据验证。
- 对 `error=0`，要求 Judge 对相关可见推理进行了充分检查，而不是仅仅没有列出错误事件。
- 对 `corrected_error`，必须在待评估轨迹原文中找到实际的替代推导，并确认其修复了所关联的错误，不能将 Judge 自己的修正视为轨迹中的修正。
- 错误是否严重应根据其数学后果判断，而不是根据该错误是否容易修复判断。
- 对正确但截断的可见前缀，若能够充分确认可见部分不存在未修复错误，仍然允许 `error=0`；这不意味着整题已经解决。
- 对无法判定是否存在未修复错误的情况，使用 unknown，而不是默认给 0。

### 3.4 不新增训练维度，增加标注元数据

将元数据按产生方分开，避免 Judge 的自我声明变成“核验通过”的依据：

| 产生方 | 建议字段 | 能说明什么 |
|---|---|---|
| Judge | `judge_reported_scope`、必要时的 `reason_for_unknown` | Judge 自报的审查范围与无法判断原因，不能证明审查充分 |
| 程序 | `structural_validation_status`、结构失败原因 | ID、关联、类型及规则约束是否通过，不能证明数学正确 |
| 审查流程 | `semantic_review_status`、`review_source`、分歧原因 | 人工或定向二次核查的结论及其来源；未审查明确为 pending |

不采用由 Judge 自填 `evidence_status=valid` 即视为可靠标签的机制。对 `progress=1` 和 `error=0`，自报“已检查全部”也不能替代证据与抽查。

这些是验证及审计元数据，不新增 Critic Head，也不改变三个辅助标签的原有语义。尽量由程序附加，Judge 只输出必要字段，避免再次扩大输出预算。训练 Mask 的决策及原因另行记录，不能把“允许用于训练”等同于“已经人工核验”。

## 4. P1：修改 Judge 及 Parser 验证机制

### 4.1 保留 V2.3 的 Span ID 协议

继续由程序切分原文、提供片段 ID，并回填实际原文。

不恢复要求 Judge 逐字复制长数学公式的旧协议。

### 4.2 明确区分原文证据与 Judge 推导

Judge 输出的数学判断应区分：

- `trajectory_claim`：待评估轨迹原文实际表达的内容，可简短转述；不使用只适用于 Student 的命名。
- `judge_verification`：Judge 为核查而完成的推理或计算。
- `supporting_span_ids`：支持事件判断的原文片段。

要求所有正向进展和实际修复必须能够追溯到待评估轨迹原文。允许一个事件引用多个必要片段；原文由程序回填，不要求 Judge 在 `trajectory_claim` 中逐字复制公式。

不能因为 Judge 自己发现正确答案，就认定该轨迹已经完成正确求解。上述是职责划分，具体字段应与现有事件结构合并，避免重复输出同一段解释。

### 4.3 将验证拆成两个层次

**第一层：结构检查**

继续由 Parser 检查：

- JSON 格式与字段是否合法。
- Span ID 是否存在。
- 事件类型是否合法。
- 错误和修复之间的关联是否合法。
- 标签是否满足基本结构约束。

**第二层：语义支持检查**

增加对高风险事件的验证：

- 原文片段是否真正支持有效进展。
- 修复事件是否存在实际替代内容。
- 所选片段是否只是计划性文字，却被描述成计算结果。
- Judge 的数学判断是否和原文内容发生明显矛盾。

实现时明确能力边界：

1. 确定性程序只检查可机械确认的约束。关键词、正则或字符串相似度不能充当一般数学证明检查器，也不能把“存在引用”当成“引用支持结论”。
2. 优先对实际修复、完整进展、无未修复错误，以及明显归属冲突进行定向核查。输入题目、必要上下文、原文片段及待核查断言，询问具体命题，例如“这些片段是否真的给出了替代推导并修复原错误”，不要求重新生成整套 Rubric。
3. 二次 Judge 的结果也是待评估的模型判断。同一模型两次一致不能视为独立真值；必须在审查集上核验它是否减少误标，以及是否额外误杀正确标签。未经验证，不将二次通过直接升级成高可信监督。
4. 首轮判断可能正确但证据定位失败时，允许一次有界的证据重新定位：从原轨迹找到支持或反驳该判断的片段，重新经过结构检查与相应语义核查。找不到、发现反证或分歧未解决时 Mask 受影响维度，不能反复重试直到得到肯定结果。
5. 每条轨迹最多增加一次定向请求；若需要重新定位，应合并在该次请求中，并计入第 7 节总预算。长轨迹上下文不足或预算耗尽时明确记为未解决，不能默认通过。线上是否启用该请求由配置控制，先验证其质量与成本。

Parser 负责结构校验和确定的 Mask 决策；模型语义核查应放在独立、可关闭的标注步骤中，保留请求、结论和版本，不能让 Parser 隐式发起额外推理。

### 4.4 保留局部 Mask

分别对 Progress 和 Error 维度进行验证，不因一个无关事件失败就清空所有监督。

但是：

- 关键错误及修复依赖未能确认时，不保留受其影响的标签。
- 不因理由描述简短而直接 Mask 数学上有充分证据的标签。
- 不把缺少证据的正向分数自动转换为 0。
- 不把 Judge 的自报 confidence 直接当作标签正确概率。

### 4.5 控制输出协议复杂度

维持当前最多四个关键事件的设计作为初始版本，不同时修改模型大小、事件数量和验证协议。

如果审计证明事件容量不足是主要失败原因，再单独比较增加事件数量的效果。

## 5. P2：优化辅助损失的稳定性

### 5.1 暂时保留 BCEWithLogitsLoss

当前 0、0.5、1 是有序程度分数，unknown 是 Mask 状态。

BCEWithLogitsLoss 可以处理 0–1 软标签，因此不必立即修改。

本轮不同时引入 Huber Loss、Ordinal Classification 等新目标，避免增加实验变量。

### 5.2 处理稀疏标签的梯度放大

当前实现先对各维有效样本求平均，再对当前有标签的维度取平均。稀疏维度中的单个标签可能获得较大的相对权重；有效维度数变化也会改变其他维度的权重。

“固定维度分母”和“按有效数量门控”是两个独立改动，不应合并后将所有效果归因于门控。保留三个可明确选择、写入配置与日志的模式：

| 模式 | 维度归一化 | 数量门控 | 用途 |
|---|---|---|---|
| `legacy_active` | 对有效维度取平均 | 无 | 复现现有实现 |
| `fixed_dimension` | 固定除以 3，未启用或无标签维度贡献为 0 | 无 | 单独验证维度归一化变化 |
| `fixed_dimension_gated` | 固定除以 3 | 有 | 在上一模式基础上单独验证门控 |

以下公式对应 `fixed_dimension_gated`；`fixed_dimension` 令所有有效维度的门控为 1，无效维度贡献仍为 0：

这里的总损失仅指 Critic 更新，不包含 Actor 的训练目标。

\[
\mathcal L_{\mathrm{total}}
=
\mathcal L_{\mathrm{BT}}
+
\lambda\mathcal L_{\mathrm{aux}}
\]

\[
\mathcal L_{\mathrm{aux}}
=
\frac{1}{3}
\sum_{k=1}^{3}
g_k
\frac{\sum_i w_i m_{ik}\ell_{ik}}
{N_k+\epsilon}
\]

其中：

\[
N_k=\sum_i w_i m_{ik},\qquad
g_k=\min(1,N_k/\tau)
\]

- \(m_{ik}\)：某回答在该辅助维度是否有效。
- \(w_i\)：若按唯一回答遍历，取 1；若按配对展开后的回答行遍历，取该回答在本次全局逻辑优化 minibatch 中重复次数的倒数，分子、分母都使用同一权重。
- \(N_k\)：一次逻辑优化 minibatch 内，跨 data-parallel rank 与梯度累积 microbatch 汇总后，该维度有效的唯一回答数。不是单卡 microbatch 数量，也不是整个 rollout 池的累计数量。
- 相同 response ID 的标签和 Mask 必须一致；去重覆盖 Teacher/Student 配对中的重复出现，沿用并核验现有去重及分布式梯度缩放语义。同题的不同回答仍可能相关，唯一回答数不能当成统计独立样本量。
- \(\tau\)：4 或 8 仅作为候选起点，先选定一个进行数值检查，不默认执行参数网格搜索。
- \(\lambda\)：0.1 只是初始参考值。归一化变化后，同一数值不代表相同的实际辅助梯度强度。

这里的维度门控用于避免极少数标签控制整维梯度，不代表标签本身已经可靠。

**实施注意：**

1. 阶段 A 的 Judge 对照保持旧 Loss 口径；阶段 B 使用固定标签分别检查三种模式，不同时更换 Judge。
2. 检查零标签、单标签、重复回答、部分维度缺失及不同 microbatch 切分，确保损失和累计梯度与单批参考计算一致。分布式缩放沿用现有约定，不额外重复乘除 rank 数。
3. Correctness-only 在固定分母模式下也是除以 3；相较旧实现，其辅助项会缩小到原来的三分之一。此变化必须明确记录，不能将旧归一化的 B 与新归一化的 C 直接用于判断过程监督收益。
4. B/C 受控对照使用相同模式、相同 \(\lambda\) 和相同 Correctness 权重；若采用门控，门控规则和阈值也相同。新增过程维度不应隐式降低 Correctness 的权重。旧模式只作为复现对照，不混入新方案的主比较。
5. 记录各维实际梯度贡献和门控前后的有效权重。少量关键错误标签也可能非常有价值，不能仅凭数量少就宣称其应被弱化；若门控持续压低这类监督，应调整或关闭该选项，而非追求平滑日志。

### 5.3 监控共享 Backbone 上的任务冲突

定期记录：

- BT Loss。
- Correctness / Progress / Error Loss。
- 各维有效样本数和标签分布。
- BT 与辅助损失的梯度范数比。
- BT 与辅助梯度的余弦相似度。

建议在固定的小型诊断 Batch 上计算梯度指标，不必每个训练 Step 都记录。

暂不引入 PCGrad、GradNorm 等额外优化算法。

### 5.4 校验在线训练的质量保护

现有零覆盖保护能够发现标签全部失效，却不能识别错误标签通过验证的问题。

建议增加标签质量监控：

- 关键错误反例的定期检查。
- Process 标签覆盖率突然异常上升或下降的告警。
- Teacher/Student 有效标签比例变化。
- Process 分数分布突然塌缩的告警。

对于通过校验但被高可信反例证明错误的标签，不应直接缓存为可靠监督。

上述监控不等于每步额外调用 Judge。优先复用已有日志和缓存抽查；额外定向请求统一计费、计数。发现旧缓存中的错误标签时保留审计记录并隔离，避免被新协议继续复用，不直接覆盖正在运行实验的缓存。

## 6. P3：受控实验设计

### 6.1 Judge 标签质量验证

在相同冻结数据与相同 Judge 模型下，比较：

| 方案 | 主要区别 |
|---|---|
| V2.3 | 当前片段协议与校验 |
| V2.4 | 新判据与证据支持校验 |

统计：

- 每维有效覆盖率。
- 保留标签的经核验正确率。
- 被 Mask 样本中的有效标签比例。
- 证据归属错误率。
- 各类数学错误的漏检和误检。
- Teacher/Student、完整/截断轨迹的分组表现。
- 每单位 Judge 推理成本获得的可靠标签数量。

同时报告原始请求数、唯一回答数、独立问题数、每维标签数和两维同时有效的比例。把结构通过率、经人工审查的正确率、仅二次模型核查的通过率分开列出；未审查项不算可靠标签。成本包括输入、Thinking、最终输出、定向核查与重试的 token 和耗时。

**过程信息的区分能力必须单独验收：**

- 在同一道题、最终答案正确性相同的回答之间，检查是否能区分正确进展、关键错误及真实修复。不能只靠“答案对的过程分高”证明过程标签有增量信息。
- 对可配对的正确前缀、引入关键错误、实际修复后的轨迹，先写出各维应发生的变化，再检查标签是否符合预期。无需强求所有变化都反映在 Progress 上，例如它可能始终为 0.5，而 Error 应随错误及修复变化。
- 检查标签是否主要在区分长度、截断状态或 Teacher/Student 来源；记录真正产生不同过程判断的问题数量，不以同题重复回答或重复标签扩大证据。
- 不强行均衡 0/0.5/1，不以标签熵最大为目标。若大量标签可靠但恒为 0.5，应如实认定当前粗粒度 Head 的区分能力有限，而不是人为改分。

8B 与 14B Thinking Judge 的比较作为后续可选实验，先在固定模型上验证协议。不能同时更换模型和 Prompt 后直接归因，也不默认启动多模型搜索。

### 6.2 Critic 训练消融

以下为用户执行的正式实验；执行模型交付配置、命令和小规模验证结果：

|---|---|---|---|---|
| A：GAD Baseline | ✓ | — | — | — |
| B：Correctness-only | ✓ | ✓ | — | — |
| C：Naive Rubric | ✓ | ✓ | ✓ | ✓ |

- Correctness + Progress。

B/C 还必须按第 5.2 节固定归一化、Correctness 的系数及门控口径。固定分母下，C 比 B 增加过程项，总辅助梯度可能增加；报告这一变化，不将 B/C 差异单独解释为过程标签的内容价值。必要时由用户补充总辅助梯度规模匹配的对照，执行模型不自动扩展正式实验矩阵。

## 7. 实施顺序与验收条件

### 分工与小规模预算

- **执行模型：** 审查已有输出，修复代码与配置，完成 CPU/固定 Batch 数值检查，准备人工审查材料，并按下述预算完成必要的 Judge 与训练链路冒烟验证。不得把模型审阅写成人工标注。
- **用户：** 确认审查结论及风险阈值，执行正式 Baseline、Correctness-only、Rubric 重跑和最终评估；需要扩大模型、样本或消融规模时再安排。
- **建议的小规模执行预算：** 每轮方案验收最多新增 24 次 Judge 请求，首轮、重试、定向二次核查都计入；只使用一个预先选定的模型与配置。GPU 验证阶段合计以 30 分钟为上限，达到任一上限即保存结果和未完成项，不自动循环续跑。这是本方案提出的默认预算，用户后续明确指定的预算优先；若既有约定更小，遵守较小预算。该上限是资源边界，不是统计充分性的保证。
- **训练链路验证：** 标签质量关卡通过后，使用最多 4 个固定 Teacher/Student 对，Warmup 与 GAD 各完成 1 次逻辑优化更新，并在各阶段验证保存后恢复的下一次更新。检查标签/Mask、BT 与辅助梯度、各阶段的原始 Actor 更新逻辑、协议配置和恢复状态；不运行整轮训练或完整数学评估。GPU 验证统一计入上述时间预算，超时记录阻塞原因。
- **实验隔离：** 使用独立配置、输出目录、缓存版本和检查点目录。不得覆盖历史实验，不修改运行中任务依赖的配置和数据，不停现有进程、不抢占其 GPU。资源不足时继续 CPU、已有结果审计和配置工作，GPU 验证明确标记待完成。

每次运行前固定样本清单、配置、请求预算与验收标准，结束时报告实际消耗。本文的实验列表不是自动启动正式训练或额外搜索的授权。

### 阶段 A：Judge 质量与验证机制

- [ ] 审查现有 V2.3 错误与 Mask 案例。

- [ ] 复核三个辅助维度的有效样本归一化。

- [ ] 阶段 A 通过后，完成有预算的 Warmup → GAD 及保存恢复链路检查。

**验收重点：** 稀疏、重复及切分条件下的损失和梯度符合定义，辅助项确实进入共享 Critic，原 BT 和 Actor 更新路径符合设定，保存恢复后状态一致。冒烟验证只能证明工程链路可用，不能证明不会影响长期 BT 学习，也不能证明 Actor 会提升。

- [ ] 运行 Correctness-only。

- [ ] 检查 Critic 排序质量与 Actor 最终表现。
- [ ] 总结 Process Rubric 是否提供增量收益。

**验收重点：** 能够区分新增过程信息的作用、Judge 标签噪声的影响，以及辅助 Loss 本身的影响。

## 10. 最终研究问题

本轮实验希望回答：

**Q1：** 调整验证协议后，能否在预先约定的误标风险范围内，保留更多有数学意义的过程监督？

**Q2：** Process Rubric 是否提供了超出最终答案正确性的有效信息？

**Q3：** 这种过程监督能否通过 Critic 的共享表征改善 Advantage 质量，并进一步提升 Actor 数学推理能力？

如果 Q1、Q2 得到支持，但 Q3 未得到支持，先检查辅助 Head 是否真正学到过程信息、共享表征是否传递给 `adv` 排序、梯度冲突和尺度、On-Policy 分布变化，以及训练预算与实现问题。不能仅因一次 Actor 未提升就认定过程监督无效，或立即切换到 Actor 直接使用 Rubric；直接奖励属于后续独立研究方案。

如果 Q1 成立，但高质量过程标签的生成成本仍然很高，则可以探索训练 Critic 承担 Rubric Judge 的角色。

如果 Q1 无法成立，则应优先简化过程判据，而不是直接推进复杂的自演化系统。

**最终原则：保留可靠、有区分力、能产生有效训练梯度的监督；减少形式化解释带来的无效过滤，同时避免错误评价通过验证。**

- `holdout_892141d32c80f673b92b` 首轮一个事件列出连续 362 个 ID，复核又在标签与事件中重复枚举。当前 `supporting_span_ids` 没有数量上限；最多四个事件不等于输出有界。

当前 `review_batch()` 在正式在线路径中逐条同步调用复核，首轮并发结束后才进入该循环。调高首轮并发不能消除复核串行等待。

本轮目标是在不改变数学判断标准的前提下减少冗余输出和串行等待。质量验收仍独立进行，不能用速度变快、非 unknown 增多或二次模型一致替代可靠性。

### A.2 固定变量与暂缓事项

固定 Qwen3-8B Thinking、模型/Tokenizer、采样参数与 Seed、当前 32k 上下文和 8192 总输出上限、TP=2、服务引擎及硬件条件；首轮与复核继续使用已有数学判据、局部 Mask、原文归属要求和最多一次额外复核的规则。

本轮不调整复核触发策略、不改成抽查、不裁剪 Judge 的完整可见轨迹，不将未知标签改成 0。保留首轮与复核读取的完整数学上下文，先只压缩输出证据表示。

本轮不实现独立 Thinking 预算、不切换 non-thinking、不更换模型、不调 Loss/Replay、不升级推理引擎或同时调整 CUDA Graph 等服务参数。长 Thinking 耗尽预算仍单独记录；本附录不能解决所有长尾问题。

### A.3 第一步：压缩证据输出

**原则：完整审查与输出关键证据分开；压缩表达不能变成删除必要数学证据。**

1. 保留现有原文分片及稳定 ID，不同时重切输入。优先增加紧凑区间表示，例如用一个结构化的起止 ID 对表示 `s24` 到 `s408`，单片段用相同起止 ID 表示。程序按原文片段顺序展开并回填，不依赖字符串字典序；禁止反向区间、越界和不存在的端点。
2. Prompt 明确要求选取足以支持断言的关键证据，不通过引用全文表示“已检查全文”。建议每事件通常选 1～4 个证据单元，初始上限为 8 个单元；一个单元为单片段或连续区间。此上限是待验证的协议参数，不是数学充分性标准。超出时报告表达容量不足并保留原始结果，不能静默截取前 8 项。
3. 对重叠区间展开后去重并保持原文顺序，原文字符偏移与内容必须可准确还原。展开范围最多为原轨迹的片段集合；程序防止重复展开导致资源膨胀。
4. 区间覆盖几乎全文时，记录证据覆盖比例和“宽泛引用”审计标记。压缩成一个区间只减少 token，不证明整段都支持断言；不能因范围大直接通过，也不仅因范围大就判数学错误。
5. 首轮与复核同时采用紧凑表示，避免只压缩首轮、复核再次展开生成。标签优先引用已核查事件；确有额外证据时再补充紧凑引用。若复用事件证据，标签仍须有自身明确的核查结论与有效依赖，不能仅将事件引用并集自动认定为标签被支持。
6. `trajectory_claim`、`judge_verification` 和理由保持简短且分工明确，不重复整段解答。必要推导仍可表达，不通过任意截断文本使 JSON 或数学含义残缺。
7. 维持错误/修复依赖语义。区间压缩后仍须按展开的真实片段检查修复证据及相关约束，不能仅比较区间对象是否不同，就认定出现了替代推导。
8. 原始模型输出、紧凑证据和程序展开后的证据分别保存。采用新的 wire/schema/cache 身份，具体编号按当前注册版本分配；旧结果保留原解释器或显式迁移，不静默套用新协议，不覆盖运行中实验的缓存。

不要直接给旧协议硬加数量限制后把大批标签 Mask，当成压缩完成；也不要恢复让 Judge 手抄长公式。结构化生成约束需验证当前引擎支持，不能因增加 schema 约束再次触发不受控的后端回退。

**先做 CPU 验证：** 将已有证据列表机械编码为区间，再展开；比较 ID 集合、顺序、原文偏移、事件依赖和各维 Mask 是否等价。覆盖连续/离散/重叠区间、无效端点、长引用、实际修复和独立局部进展。这只能验证无损编码；模型改用新协议后是否仍选对证据，需要第三步验证。

等价性以去重、按原文顺序排列后的证据集合为准，原始列表仍保存以供审计。不得把不连续的 ID 简单合并成最小/最大端点区间，从而引入原来未引用的片段；必须分成实际连续的区间。若无损表示超过约定的单元容量，单独报告容量冲突，不能为通过等价性检查而改变证据或旧标签。

### A.4 第二步：首轮与复核共用有界并发调度

将每条轨迹组织成“首轮 → 判定是否复核 → 最终解析/持久化”的任务链。不同轨迹可以并发；同一轨迹的复核只能在其首轮成功并命中原触发条件后提交。

- 使用统一的全局在途请求上限，首轮与复核共同计数，不使用两个独立线程池各放满配置并发。
- 首轮结果完成后即可安排该条复核，不必等待整批首轮结束。采用简单公平队列，避免持续提交首轮导致复核一直排不到。
- 保留每条轨迹最多一次复核、无不变输入重试、全局请求预算与共同 deadline。预算检查和预占必须原子化；任务入队不算已发送，实际发送尝试才计入请求消耗。
- 明确单请求超时与整批截止的区别，记录排队、实际 API 等待和复核等待时间。客户端 future 取消不代表服务器已停止生成；在途请求与清理状态如实记录，不能靠重发隐藏超时成本。
- 结果按稳定 request/response ID 归属；由协调方安全写日志、缓存和最终标签，不依赖完成顺序。复核一次性状态、请求预算与恢复状态沿用现有保护，避免恢复后重复提交已完成请求。
- 不在持有全局请求许可时同步等待子复核申请同一许可，避免并发 1 或线程池满载时发生死锁。每次实际 API 调用独立获取/释放许可，轨迹依赖由协调方推进。
- 并发 1 必须仍能运行。新增并发 2 作为本轮默认吞吐比较；并发 4 仅在预算剩余且并发 2 结果稳定、显存允许时再考虑，不默认展开搜索。
- 基准脚本和正式在线标注必须复用同一调度实现，不能仅在离线工具中并发而保留生产串行循环。评分模型、采样参数与 Seed 的生成方式保持不变；批处理数值差异仍可能影响生成，须逐条对照。

CPU 使用可控的模拟请求检查最大在途数、依赖顺序、预算竞态、超时、失败局部保留、重复请求和恢复。不得用假请求的吞吐证明真实 GPU 提速。

### A.5 第三步：固定样本的质量与耗时对照

**样本：** 固定本轮已处理的 8 条回答作为开发诊断池，保存题目、原文、身份与哈希。至少覆盖长证据枚举、证据字段丢失、Student 局部进展/错误、Thinking 耗尽预算等已有模式。该池已经用于定位和修改协议，应从原留出集转为开发集，不再宣称独立质量验收；未生成数据的留出资格须按题目检查，同题回答不能算独立留出。

先确定一个 4 条的最小 GPU 对照子集，建议包含两个长列表案例 `holdout_892141d32c80f673b92b`、`holdout_89380c260abbc37f298f`，以及 `holdout_9c77c7446f563e8962e1`、`holdout_0544c0284caefe14fadb`，覆盖 2 条 Teacher 和 2 条 Student。其余样本用于已有结果审查与 CPU 回放；扩大 GPU 样本前先检查预算。

| 比较项 | 证据协议 | 并发 | 用途 |
|---|---|---|---|
| B0 | 原 v2.4 实施协议 | 1 | 已保存基线；必要时有预算地补测 |
| B1 | 紧凑证据协议 | 1 | 隔离输出协议变化及其质量影响 |
| B2 | 与 B1 相同 | 2，共用新调度器 | 隔离并发调度对吞吐和结果的影响 |

以上 B0/B1/B2 是 Judge 微基准，不是正文的 Critic A/B/C 正式训练实验。B1/B2 均使用新调度器，分别配置并发 1/2。优先复用已保存 B0；历史 B0 与新运行的耗时比较标明服务状态和时段差异，只作为参考，不能声称严格同窗口加速比。B1/B2 尽量在一次服务启动中完成，模型加载单列，禁止跨组标签缓存命中跳过生成；组内仍按原规则去重。

B1/B2分别使用独立输出、缓存及复核去重状态，避免第二组因相同ID被判为“已经复核”而跳过请求；全局成本账本仍共享，不能重置预算。记录各组实际完成的同一批回答及首轮/复核数。若并发改变生成内容、长度或触发率，吞吐差异包含工作量变化，须与纯调度收益分开解释；超时样本不能从分母中悄悄删除。

四条回答、两组、每条最多两次请求，B1/B2 最多需 16 次生成请求。沿用正文建议的共享 24 次/30 分钟小规模窗口，首轮、复核及必要基线补测全部计入，用户另有明确预算时以其要求为准。两组共享额度，不能分别重置；若未跑完，保留部分结果和未完成项，不为了凑齐对照无限续跑，也不把前一轮已消耗预算当成此次自动获准的额外实验。当前文档修订本身不执行 GPU 验证。

**必须记录的指标：**

- 每请求输入 token、API 总输出 token、Thinking/最终 JSON 的独立估计及其来源；不能混加不同计量。
- 每事件证据单元数、展开后的唯一片段数、跨事件重复量、全文覆盖比例；标签与事件重复输出量。
- 首轮与复核各自的请求数、实际复核触发率、API 耗时、排队时间、超时、预算耗尽及 JSON 失败。原触发函数不变不代表新生成输出的实际触发率一定不变。
- 整批墙钟时间、回答吞吐、输出 token 吞吐、实际在途请求峰值、显存及 OOM；少量样本优先列逐条时间与中位数/最大值，不用不稳定的 p95 包装确定结论。
- 各维原始/最终分数、Mask 原因、来源与截断分组；尤其检查 Student 的 Progress/Error 是否进一步丢失。
- 盲审材料和逐条证据对照：分数是否正确、原文是否支持、是否出现自算归属、假修复或关键错误漏检。人工未完成时准确率保持 pending，不把首轮/复核一致当真值。

**验收与交付：** 无损展开及调度 CPU 检查通过；B1 的证据冗余显著减少且逐例差异可解释；B2 的整批吞吐相对 B1 有实测改善，不能用请求耗时之和比较并发收益。任何新关键误接受、独立进展丢失或错误监督恶化都应单列，先修查明原因，不以提速抵消。若质量尚未人工确认，只交付“工程/吞吐验证”和待审材料，不宣称监督能力已提高或正式训练已就绪。

“提速”是待检验假设，不是要求执行模型必须跑出正结果。若B2没有改善或超时增多，应如实交付结果并保留并发1，不在本附录范围内自动反复调参或延长实验。有效标签数量与经人工核验可靠的标签数量分开报告；后者尚不可得时，不计算“可靠标签/分钟”。

| Replay | 关闭 | 继续关闭 |
| 梯度诊断 | 每100步，最多4个配对 | 保持相同 |
| 外部自动评估 | `eval.enabled=false`、`eval_after_train=false` | 用户后续统一评估，不假定训练结束就有正式成绩 |

Correctness-only配置虽然仍列有Judge参数，但当前模式不创建过程Judge，过程维度被Mask；其中non-thinking/768输出预算不会用于过程评分，不是需要修改当前实验的理由。

当前模式对三个辅助维度固定除以3。以各维有效回答平均损失 `L_c/L_p/L_e` 表示，`g_k=min(1,N_k/4)`：

```text
Correctness-only：L_BT + (0.1/3) × g_c × L_c
Rubric joint：    L_BT + (0.1/3) × (g_c × L_c + g_p × L_p + g_e × L_e)
```

无标签维度贡献为0；N是全局逻辑优化minibatch的去重有效回答数。两组Correctness系数规则一致，加入过程项不会因增加有效维度而自动降低Correctness权重。两组On-Policy轨迹和有效数量可以自然不同，不要求实际梯度完全相同。Joint总辅助梯度可能增大，需要记录，本轮不额外展开权重网格或等梯度消融。

**覆盖顺序风险：** 现有 `rubric_v24_8b_thinking.yaml` 写有 `loss_mode: legacy_active`，用于早期Judge对照。后续必须最后加载 `rubric_v24_loss.yaml`，并检查生成快照；不能仅凭文件名认为两组Loss相同。

- 增加明确的验证诊断开关，建议为 `validation.rouge_l_enabled=false`（拟新增，当前不能当作已有参数使用）。数学任务默认关闭；需要复查文字相似度时显式开启。配置解析、快照、启动计划与验证产物都记录该开关。

### C.6 数学正确率到底由什么计算

以下为 2026-10-17 读取实现后的现行口径说明；本附录不新增评分标准，也不重新引入 CARD/OPRD 两套主分数。

**先给每条回答判对错，再做不同方式的统计。** 统一入口为 [scoring/math.py](../scoring/math.py)，版本 `math_unified_v1`。训练 correctness 标签和新外部评估均复用这个入口；规则判分不调用 LLM Judge，也不检查整条推理过程是否正确。

单条回答的判分过程：

1. 从回答中的显式答案提取结果，例如 `\boxed{...}`、`Answer:` / `Final answer:`，支持答案在下一行；按当前规则排除可识别的模板占位后选择最后一个显式答案候选，末尾出现损坏或歧义答案时不偷偷退回更早答案。提取阶段不看标准答案。
2. 检查数学对象结构，例如集合、序列/区间括号、单位与条件。集合按无序元素匹配，序列按位置匹配；不随意丢弃单位或边界条件。
3. 在兼容结构下依次使用规范化后的精确相等、受限数值语法的 MathD 快速判等、SymPy 符号化简判等。这些是一个 scorer 内部的判等步骤，不是三种独立准确率，也不是投票。当前不使用宽松数值误差阈值；条件/方程不进行一般等价证明，规范化后不相等便判不等。
4. 判对为 1、判错为 0；没有显式最终答案也按 0 计。答案格式损坏、歧义、判等超时或异常则不可评分。response 被截断不自动改判错，仍按可见答案处理并单列截断率；训练题目本身不可用/被截断时，correctness 标签另有 Mask 保护。

| 字段或指标 | 含义与使用范围 |
|---|---|
| 训练验证 `acc` | 全部可评分时的回答正确数 / 验证回答总数；本次每题 1 条、共 512 条。不可评分时为 null，不作为完整正式成绩 |
| 训练验证 `provisional_acc` | 固定总分母下的临时值；未知样本不增加正确数，必须与 incomplete 状态一起展示，不能用它替代正式 `acc` |
| 外部评估 `pass_at_1` | 每题的 n 条回答中正确比例，再对题目平均；估计一次采样的成功率，不是“n 次里任意一次答对” |
| `sample_accuracy` | 所有正确回答 / 预期回答总数；每题相同 n 且数据完整时，与上述 `pass_at_1` 相同，不是第二套判题规则 |
| `first_rollout_accuracy` | 仅统计每题 rollout 0 的正确率，用于辅助观察；不能与使用所有 n 条估计的结果混名 |
| `any_success_at_n` | n 条回答中至少一条正确的题目比例；是多次尝试成功率，不是单次回答准确率，也没有让模型自行选择最佳答案 |
| `score_mean` | 兼容旧接口的分数均值；可评分回答使用 `2×correctness−1`，完整时等于 `2×acc−1`。不是新准确率，也不是过程分；有不可评分样本时不按此等式解读，应连同完整性状态标注为诊断 |
| 解析失败率、无答案率、评分器错误/超时率、不可评分数/率 | 说明评分质量和失败来源，不参与加权合成“数学总分” |
| 截断率、平均输出长度、生成/评分耗时、样本完整性 | 运行诊断；不加到正确率中 |
| ROUGE-L | 独立的文字相似度诊断；按本附录默认关闭，不影响数学判等 |

外部聚合实现见 [evaluate/rescore.py](../evaluate/rescore.py)。若样本缺失、重复、索引异常或存在不可评分回答，正式准确率相关字段移入 `provisional_metrics`，记录 `evaluation_complete=false`，不缩小分母来抬高结果。旧 `card_metrics.json` 及 OPRD 对照在汇总脚本的历史兼容模式中仍可读取，仅用于历史审计；新正式比较使用统一 scorer 的 `metrics.json` 及一致的版本指纹。

注意：统一评分不等于统一实验条件。训练开发集的单次确定性验证，与外部数学基准的多次采样，数据、n、温度等可能不同，不能直接把两个百分比当作同一条件下的成绩。
