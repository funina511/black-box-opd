## 2. 本次核查结论

### 2.1 当前运行确实偏保守，但 offload 不是唯一成本

实际配置见 [实验快照](../runs/baseline_06b_17k/train.yaml)：0.6B、四卡、batch=64、GAD n=2、response 上限 8192；Actor/Critic 参数及优化器 offload 均开启，Reference offload 开启，gradient checkpointing 开启，Critic microbatch=1，vLLM eager=true、显存比例 0.55、TP=1。Rubric、Replay 都关闭，当前 baseline 的慢不是 Judge 造成的。

截至本次核查，GAD 日志已记录 step454。下表来自各阶段最近 20 个正常训练步，排除保存和验证步；GAD 为 step434–454 中排除 step450，包含 20 步。日志还在增长，数字是本次观察窗口，不是整轮固定耗时。

| 平均耗时/特征 | SeqKD（522–541） | Warmup（251–270） | GAD（434–454，排除450） |
|---|---:|---:|---:|
| 每步总耗时 | 17.94 秒 | 281.76 秒 | 462.95 秒 |
| `gen` 整段 | 1.43 秒 | 193.89 秒 | 277.03 秒 |
| 其中 `generate_sequences` | 0.002 秒 | 179.25 秒 | 244.80 秒 |
| Critic 更新 | 无 | 48.58 秒 | 98.61 秒 |
| Actor 更新 | 16.51 秒 | 18.45 秒 | 50.13 秒 |
| Student 平均输出长度 | 训练不生成 Student | 6815 token | 5842 token |
| Student 达到长度上限比例 | 不适用 | 71.1% | 54.1% |

GAD 的 `gen` 约占每步 60%，Critic 更新约 21%，Actor 更新约 11%；其余包括 old logprob、Reference 和 reward forward。`generate_sequences` 是 `gen` 的内部计时，不能相加重复计算。Warmup 的生成成本同样突出。SeqKD 训练直接使用已有 Teacher 回答，不承担相同的在线生成成本，因此不能期待只调一个 offload 开关就获得 SeqKD 的速度。

本机为 24 GiB RTX 3090。一次只读 GPU 快照中训练卡约使用 8.4–9.3 GiB、GPU 利用率 100%；这只是某个执行阶段，不能据此判断训练峰值或证明全部 offload 都可以关闭。日志中的 `perf/max_memory_allocated_gb` / reserved 曾超过 24 GiB，它们是当前框架的进程/历史 allocator 统计，不能直接当作单卡当前物理显存；具体与 vLLM sleep/allocator 的关系需核对，不在本计划中猜定原因。

### 4.3 有限性能候选，优先不改变优化目标

第一轮保持 batch=64、Warmup n=1、GAD n=2、2048/8192、学习率、梯度裁剪、逻辑 minibatch 和更新次数不变。默认先在本机4×3090上筛选，目标服务器按机器配置重新确认。

| 候选 | 改动 | 要回答的问题 |
|---|---|---|
| P0 | 当前配置控制组 | 同一工具下的真实基准是多少？ |
| P1 | 关闭 Actor/Critic 参数和 optimizer offload，Reference 暂保持开启 | 0.6B 常驻是否装得下、能省多少搬运时间？ |
| P2 | 在可用的 P1 上 Critic microbatch 1→2；逻辑 minibatch 不变 | 减少小批量调度是否有效？长 Teacher/Student 同时前向能否承受？ |
| P3 | 在可用配置上测试 `enforce_eager=false` | CUDA graph 是否降低占比最大的生成耗时？其初始化、图缓存与显存成本如何？ |

这些是筛选候选，不要求全部组合或全部通过。P1 若 OOM，回退为仅关闭 optimizer offload 或只保留一个角色的参数常驻，替代后续低优先级候选，不无限扩展矩阵。Reference offload=false 在开关修复后做短功能确认，是否纳入最终性能候选视剩余预算而定；它当前仅对应约12秒/步的 ref 段，不应抢占生成瓶颈的全部调优时间。

Actor token budget 增大、Critic microbatch=4、关闭 gradient checkpointing、提高 KV 显存比例、TP变化为第二顺位；只有第一轮指出明确瓶颈且仍有预算时才替换一个候选。KV缓存、常驻模型、optimizer 和 CUDA graph 共用显存，不能只按0.6B权重大小推算。保留 allocator 与 vLLM CuMem 的已知兼容限制，不随手开启 expandable_segments。

Actor 动态 token microbatch 的分组会影响变长样本的损失加权，不能宣称改变 token budget 必然数值等价。Critic microbatch 也必须验证 BT、辅助去重权重、全局有效数、DP和梯度累积的归一化。

启动计划必须输出：数据条数、drop_last 尾部条数、每轮步数、各阶段起点/新增/累计步数、预计 Actor/Critic 更新次数、采样回答量、验证和保存次数。当前17405条、batch64时每轮271步，通常丢弃尾部61条/轮；核对 shuffle 和 sampler 的实际策略，不临时修改尾批处理。

**身份修复 M2：** 新运行的数据/模型/Prompt/协议以内容身份为主，路径与文件stat用于部署定位或哈希缓存，而不是认定“同一模型”的唯一依据。Judge目前把inode/mtime/ctime和绝对路径放进fingerprint，普通复制就可能改变身份；stage signature也含绝对模型/数据路径。应版本化新身份格式，首次迁移按实际内容hash校验并产生来源映射，旧记录只读兼容。不能简单忽略fingerprint、改旧缓存头或强行让不匹配checkpoint通过。

**首版范围（2026-10-19 修订）：** 第一批 17k 先采用**旁路内容身份**：在新 manifest/report 中记录模型、数据、Prompt、协议、teacher index 和初始化 critic 的内容 hash，同时保留旧 fingerprint、旧 cache 和旧 checkpoint 的原解释路径。首版不强制切换新 fingerprint 格式，也不因路径/stat 差异重写旧身份；路径无关的新格式作为后续版本单独验收。这样优先保证可追溯和可迁移，不把身份重构变成正式实验的阻塞项。

迁移验收分开：同内容资产在不同根目录下启动新实验；已有run完整恢复；改变GPU拓扑恢复。第一项为必需，第二项在同拓扑完成有限检查，第三项未实现重分片时应明确拒绝，不承诺任意卡数可直接恢复。旁路 hash 只能证明内容一致，不能自动让依赖旧路径/stat 的恢复校验通过；若异路径续训仍被拒绝，应明确交付“可迁移启动新实验，异路径续训尚不支持”，不要临时堆叠兼容层或关闭校验来宣称完成。

**GAD 阶段身份（N2/N3）。** 迁移与恢复前必须修好两件事：GAD 的 stage signature 绑定 Warmup handoff（N2），以及 rubric/replay checkpoint 的阶段完成校验要求 `training_extensions`（N3）。只复制 HF 权重或漏拷 `training_extensions/` 不能算“已有 run 完整恢复”；旧 marker 没有 handoff 身份时不能仅凭配置签名相同就跳过 GAD。迁移包应包含这两项的 CPU 证据，而不是只列文件清单。

## 5. 第三步：有限工程验证与停止条件

### 5.1 CPU与离线检查先行

- 数据迁移全量一致性、候选歧义、索引缺失、Teacher截断来源、17k V2 的 `.stats.json` 和 manifest 覆盖；5k 缺统计保留历史说明，不修改旧实验输入。
- 配置覆盖优先级、三方法的最终loss/Judge/seed/数据身份、角色offload与checkpointing透传。
- 实际生成的三个backend编译/补丁校验；Reference开关行为及Warmup单次恢复调用测试。
- 保留附录C的评估不完整可交接与训练故障仍阻断回归；不重做已完成修复。
- 固定保存回答上的BT、correctness/joint辅助损失、microbatch和DP归一化对比。无标签Mask、去重和固定分母保持一致。
- 完成 A.9 R1–R6 的 CPU 夹具：guard 分类、复核 `event_ids` 回写、Prompt/协议身份、四头 spec 校验、response_id/visibility 冲突和事件引用合法性；schema 改动先做 tokenizer/xgrammar CPU 编译检查。
- 完成 A.10 N1/N4/N5/N7/N8 的 CPU 夹具：invalid `unjudgeable` 不能得到 progress=1/error=0；spec/prompt 协议版本不匹配必须启动失败；`progress=1 + error=unknown` 的预期行为；空证据事件的 prompt/parser 一致性；空 response 是可诊断的跳过/Mask 还是明确拒绝。
- 完成 A.10 N2/N3 的 CPU 夹具：不同 Warmup handoff 不能命中旧 GAD 完成标记；rubric/replay checkpoint 缺少 `training_extensions` 时阶段不得判 complete，恢复必须明确失败。
- 完成 A.10 N9 的评估夹具：非连续 expected question ID、越界 rollout、重复/缺失/未知 question 都进入预期集合或完整性失败，不进入正式分子。
- 在不同临时根目录演练路径解析、manifest和内容身份；不复制整个数十GB资产来做单元测试。

只运行与修改相关的测试和必要既有保护套件，不为文档/归档移动新增镜像实现的无效测试。

### 5.2 GPU性能窗口有限，不能变成一轮新训练

首轮只安排**一个性能窗口，上限 180 分钟**，包括启动、OOM 失败和必要回退；资源只允许 120 分钟时，执行前记为 120 分钟并按该上限停止，不能事后追加另一个窗口。默认只做**控制组 + 1 个候选**，每个最多 1 步预热 + 2 步观测；只有前两项已完成且窗口仍有余量时才增加第 3 项。以当前约 8 分钟/GAD 步估算，4 项共 12 步就约 96 分钟，还未计初始化和清理，因此不默认做满 4 项。

现有 baseline 日志可用于选瓶颈和历史参考。只有源 checkpoint/数据位置、阶段、拓扑、计时口径等可比时才能替代同条件控制；否则若为省时间省略新控制短测，必须写明是探索性观测，不能声称严格对照的加速倍数。少量步骤不能支持稳定 P90。

- 使用独立后端和输出，源run只读。性能短测不在当前baseline运行期间争抢训练GPU；空闲卡单独做worker检查也不得触发全局Ray清理或共享服务改动。
- 优先GAD，因为当前总成本最高；通过候选再对Warmup做有限确认。无需每个候选都把SeqKD/Warmup/GAD跑一遍。
- 必须覆盖17k中长Teacher、长Student、8192上限附近回答，不能只用极短轨迹验证显存。microbatch损失对比可用保存轨迹；吞吐结论须包含实际Ray/vLLM与目标DP拓扑，不能用单卡worker速度代替。
- 若在所选窗口内无法获得足够证据，交付最有依据的保守可用配置和剩余候选，停止追加搜索。不给未通过长轨迹测试的全驻留配置贴“正式推荐”。

### 5.3 保存恢复与完整调用链补验

已有B/C报告完成的是真实worker更新/保存加载，不是完整多rank Ray/vLLM流水线。尊重已有结果，不重新做Judge数学评测；本轮补足完整入口与迁移真正需要的边界。

在候选确定后，用17k派生的小规模工程输入完成一次多rank Warmup→GAD交接及同阶段跨进程恢复。验证恢复前后optimizer step、scheduler、RNG、数据位置、四头布局/adv权重、辅助状态、下一步参数更新；Warmup Actor早期门槛仍按原算法，不为了测试绕过。另按 N2 验证“不同 Warmup handoff 不会命中旧 GAD 完成标记”，按 N3 验证“缺 extension state 的 rubric/replay checkpoint 不会被阶段完成校验放行”。

Correctness-only可先覆盖不依赖Judge的四头路径；joint复用既有冻结输出做损失/缓存测试，再只做最少量新在线请求检查实际协议与调用链。标记复用来源，不能把旧轨迹标签贴到新轨迹。Judge这部分建议最多4个新回答、最多8次生成请求（含复核/重试）、30分钟，执行前显式记录边界；不扩展为新一轮Judge搜索。完整链路验证另给建议最多60分钟训练窗口；与性能检查可复用成功的保存恢复证据，不能把两套测试机械重复。

### 5.4 Joint的成本必须单独交付

当前baseline没有Judge。B/C已有4条开发样本估计约69秒/待标注回答；此前给出的每步数小时只是小样本外推，不是正式batch测量。17k将放大这部分成本，关闭训练offload并不能解决Judge等待。

保留冻结Judge方案，报告：逻辑step新增Teacher/Student数量、去重后数量、Teacher跨阶段缓存实际位置与命中、复核比例、输入输出token和超时。batch64、GAD n2冷缓存通常最多涉及64Teacher+128Student；实际以选中的Critic批与去重统计为准。

用已有结果及有限在线检查给出成本区间和假设，尤其核对当前全步deadline。延长deadline只是允许等待，不是提速。不得为了让报告好看而默认减少过程标注覆盖、关闭Thinking或复核；若成本不可接受，将可选设计变更单列交给用户决定，不能擅自改变已冻结实验方法。

## 6. 第四步：冻结并交付正式17k实验

执行模型不启动完整实验。交付至少包含：

1. 新17k派生数据与内容一致性报告、输入/输出/索引指纹、Teacher 截断统计（含 `truncated_before_final_answer`、`at_or_over_limit`、`source_truncated`）和 N6 的 correctness 口径说明。
2. 当前baseline到新版本的差异表：纯元信息、纯诊断、性能执行方式、可能改变优化行为的项分开列出；N2/N3 带来的阶段完成/恢复身份变化单列，不能混在“纯诊断”里。
3. 三方法完整配置：baseline、correctness-only、rubric_joint；共同0.6B初始Actor与匹配的Critic adv初始化、相同数据/预算/seed/评估；SeqKD仍为独立基线，不接入Warmup初始化。joint 配置还必须附带 A.9 R1–R6 与 A.10 N1/N4/N5/N7 的修复映射、CPU 回归结果和“未完成项”；上述项目未完成时不得把 joint 配置标成 frozen；R7 与 N10 未完成项单独列出。GAD 配置/迁移说明还必须包含 N2/N3 的修复证据。
4. 至少一份本机已验证机器配置、目标服务器填写模板、角色实际offload状态、性能短测和显存证据。未测配置明确标记candidate。
5. 迁移运行包与归档清单、环境与固定源码、资产内容清单、新路径预检和同拓扑恢复说明。
6. 用户可复制的preflight、dry-run、训练、恢复、导出、评估命令；命令必须与最终实现字段对应，不能把本文拟新增字段当作现成接口。评估命令必须带上实际 expected question ID 集合/文件（N9），不能只传样本数量。
7. 已完成/未完成验收、GPU成本、已知限制；不把模拟测试算成真实多卡更新，不把Judge质量或Actor提升写成已证实。

正式实验始终使用17k。优先保留当前baseline的有效结果；如果新的性能方式在固定轨迹上的更新不等价或更改了优化预算，应显式采用匹配的新baseline，是否重跑由用户安排。不能将不同训练预算的结果直接归因于Rubric。

统一评估沿用 `math_unified_v1` 和冻结的采样条件，主指标为约定数学基准的单次成功率估计；first/any-success、截断与评分完整性分列。训练开发集quick与full、不同checkpoint和外部测试成绩不可混用。当前GAD step400 quick=0.1875与SeqKD final full=0.125不是同范围/同进度对照，不据此下结论。

## 7. 执行顺序与完成定义

**本节是唯一执行顺序。** “可并行”表示没有先后依赖，不要求增加执行代理、同时改同一文件或同时启动 GPU 工作。

1. **保留正常路径证据。** 只读记录当前 baseline 的配置、backend、已完成 checkpoint 和阶段交接证据，注明观察时间；运行中的日志不是已经冻结的整轮结果。复用或补齐第 1.2 节的正常交接 CPU 回归，再改阶段控制。
2. **按问题做局部修复，四组可独立推进。** 表中各组不互相等待全部完成；同一文件的修改按小补丁顺序落地。

| 工作组 | 范围 | 真正的前置关系 |
|---|---|---|
| 数据与评估 | D1、S1/S2、E1/E2/E3、N6/N9 | 新 Rubric run 需要 D1；评分发布需实际 expected ID 与完整性检查。S1 的非默认过滤、S2 的新采样身份不阻塞使用已冻结 Teacher 的性能短测 |
| 恢复与阶段控制 | F3、J1、N2/N3 | 新 GAD 的完成/跳过判断需要 N2；启用 rubric/replay 的阶段完整性需要 N3；在线 joint 的可靠故障恢复需要 J1。不能只当作远期迁移功能，但不阻塞数据准备和关闭 Rubric 的独立性能短测 |
| Rubric 协议 | R1–R6、N1/N4/N5/N7，N8 先核实实际触发条件 | 在冻结新 joint 前完成对应修复/语义说明和 CPU 回归；N5 不预设必须收紧所有 unknown 标签，N7 只对齐必要协议表述。N1 与 R1 分别验收 |
| 配置与提速 | C1、F1/F2、T1、M1，M2 首版内容记录 | 在方法/机器配置及相关 CPU 检查通过后即可做有限性能验证，无需等待全部 Judge 修复。不同时引入 batch、loss 或数据选择变更 |

3. **先验收相关 CPU 路径，再进入一次有限 GPU 验证。** N10 将相关回归接入现有入口；baseline/correctness-only 的检查不等待无关 Judge 项。按 5.2/5.3 的一次预算安排性能、多 rank Warmup→GAD 和同阶段恢复，复用证据；joint 在线检查前必须先通过其协议和 J1 检查。阶段控制还必须通过正常交接，而不只是“错误情况能报错”。
4. **分方法冻结并交付。** 同内容 17k、三方法配置、实际开关、改动清单、兼容限制和真实成本分开列出。joint 完成协议前置后再冻结，不把 baseline/correctness-only 的已完成部分拖入无限 Judge 调试。归档、R7 中非关键整理和通用 fingerprint 重构后置。
5. **用户启动正式 17k 实验。** 执行模型不跑整轮，不擅自重跑当前 baseline。N6 默认保留现有答案成功定义；要改变 Mask/过滤策略时，单列方法差异后再由用户决定。

新增问题的范围、验收与预算合并规则见附录 A；不新增一轮 5k 效果实验，也不重复消耗原计划的 GPU 验证预算。

归档清理可在依赖清单明确后进行，不应阻塞关键数据/性能修复，也不能在当前实验结束前删除其运行依赖。未指定新服务器时，以本机不同根目录的可重建验证交付，明确新机器尚未验收。

完成标准是：用户能够在同内容17k上用清晰配置启动三种方法，知道每阶段实际做多少更新、每个开关实际是否生效，能可靠恢复，并能按文档在新服务器准备运行；不是要求执行模型先证明GAD或Rubric超过SeqKD。

### A.2 J1：Judge 技术故障恢复

涉及 `gad/extensions/annotation_journal.py`、`annotation_scheduler.py`、`judge_client.py`。用通俗的话说：成功标签可以直接接着用，但“上次服务超时”不能永远作为这道题的最终结论。

1. 将成功完成、确认技术失败、尚未提交、已提交但结果未知分开记录。区分技术失败与合法的低置信/Mask 标签，不把二者混为重试条件。
2. 保留稳定的回答/缓存身份，另设标注尝试编号或恢复轮次。journal 记录每次首轮和复核的状态、失败原因、提交时间、累计请求数及预算消耗；不能通过删除旧日志绕过问题。
3. 成功结果直接复用。确认技术失败可以按显式策略有限重试，跨进程恢复后仍受累计上限约束，不能每次重启重新获得无限额度。
4. 对“已提交但结果未知”，服务端支持查询时先查状态；不支持时保留未知状态，只有显式恢复策略允许才开始新尝试，并记录可能重复计算的成本。不能声称本地超时等于远端任务取消。
5. 将复核“一次”的约束限定到一次标注尝试。修复 Client 生命周期内 `targeted_ids` 对失败回答的永久阻断，但仍维持每次尝试最多一次数学复核；技术重试不得悄悄变成多轮数学审稿。
6. 达到上限后给出可诊断的错误和恢复办法，保留现有全部失败/覆盖率不足保护，不能用默认零分放行训练。

**CPU 验收：** 成功恢复零网络调用；已确认失败按配置重试并达到上限；首轮/复核提交前后崩溃分别覆盖；未知提交状态不被当成未提交盲目重发；跨进程请求计数连续。复核测试必须覆盖“前次技术失败、后次允许新尝试”。网络使用模拟客户端；实际在线验证并入第 5.3 节预算。

旧 journal 必须有兼容读取或明确拒绝/迁移说明。旧失败不能假装成功，也不能无记录地丢弃。

### A.3 E2：评估重复执行与中断续跑

涉及 `evaluate/evaluate.py`，与正文 E1 的入口整理合并实施。

1. 分离**内容身份**与**执行状态**：模型/checkpoint、数据、采样参数、scorer 协议决定是否属于同一次评估；`ready`、`needs_export`、导出清单路径等只描述执行进度。不能比较整个可变 model 字典来判断设置是否改变。
2. 每个“模型 × 任务”分别记录生成、评分、完成状态，并核验文件内容、预期数量和身份。状态与产物采用可恢复的写入方式，避免仅凭某个文件存在就认定完成。
3. 相同命令再次执行：完整且验证通过的任务直接跳过；raw 完整而评分缺失时只评分；raw 未完成时复用原采样断点补齐。前一个任务已完成不能阻止后续任务恢复。
4. 保留禁止覆盖有效历史 `metrics.json` 的保护。需要重新评分时使用独立评分版本/输出位置；不完整评分也保留原因和旧产物，补齐后形成可追溯的新结果。
5. 模型、数据、seed、n 或评分协议真正变化时，要求新评估身份或明确报错；不能因修幂等性而放松这些检查。导出完成本身不构成内容身份变化。

**CPU 验收：** 模拟首次导出后重复执行；已完成任务二次执行没有生成/评分子进程；任务一完成、任务二中断后只恢复任务二；raw 完整时不重复采样；配置真实变化、损坏指标、写入中断均能识别。不要为验证控制流重跑完整 MATH500。

### A.4 S1：sample 的不可评分候选

涉及 `sample/build_gad_data.py`。统一 scorer 的 `None` 表示当前不能确定分数，不等于正确，也不能不留记录地当错误处理。

1. 在转换数值前检查 scorer 状态和分数有效性，区分可评分、不可评分以及 grader 技术失败；两种过滤模式 `correct`/`correct-nontruncated` 同时覆盖。
2. 建议默认策略：不可评分候选记录原因并继续检查其余候选；存在符合过滤条件的正确候选时按既定顺序选择。没有可用正确候选且存在未决候选时，单列 unresolved，默认给结构化错误及汇总；若提供跳过策略，必须显式启用并统计被移除的问题。
3. 保留正常“没有正确候选”和技术故障的区别，不把 grader 超时伪装成数学错误。该修复不改变 `all` 的选择语义，也不重新筛选已冻结的 17k 数据。
4. 同步更新过滤说明、返回状态和相关旧文档，清理同一路径中造成 scorer 来源混淆的重复 import。

**CPU 验收：** malformed/ambiguous、无最终答案、grader 失败、后续候选正确、全候选未决、正确但截断等案例；确认 `all` 的选择结果和文本内容不变。使用确定的本地夹具，不调用 Judge。

### A.5 S2：新采样的版本与内容身份

涉及 `sample/sample_teacher.py`、`sample/teacher_engines.py`。这是让未来能够判断“这些回答是否用同样条件生成”，不要求重采当前 Teacher 数据。

1. 在写 header 和分配 GPU 前，通过包元信息取得 vLLM 版本；缺失依赖或版本不可确认时明确报错/记录不可验证状态，不将 null 当作有效且相等的版本。
2. fingerprint 纳入模型、tokenizer、chat template 的内容身份，以及影响生成的实际参数。相同路径下替换权重或模板也必须被检测到；大文件哈希可通过可信清单复用，避免逐条回答重复计算。
3. 生成前用 CPU 模板预检确认 Thinking 等开关实际生效。若不支持所请求模板参数，默认明确失败；若保留兼容路径，必须显式选择并使用不同的实际身份，不能以请求值冒充实际值。
4. 新采样配置显式 seed，并说明更换批量划分、断点位置或引擎版本后的复现边界。历史 Teacher 的 `seed=None` 与训练 rollout seed 是不同设置，不据此修改历史记录。
5. 旧 header 只读保留，用文件内容哈希和已知来源冻结旧数据，未知版本仍标记未知。禁止用今天的版本回填冒充历史版本。新旧身份不兼容时拒绝追加到旧结果，使用新输出路径。

**CPU 验收：** 懒加载引擎尚未启动时版本已可核验；模型/tokenizer/template 同路径内容变化阻止续写；模板参数不支持时明确处理；相同身份正常续跑；旧 header 不被重写。与 D1 的 17k 元信息迁移共用内容一致性证据，不额外生成 Teacher 回答。

### A.6 E3：异常评估索引与固定分母

涉及 `evaluate/rescore.py`。分母约定有几条回答，分子就只能来自这些回答；不能把多出来的回答也算进去。

1. 明确预期集合为“预期 question ID × rollout 0…n−1”。越界、负数、非法类型及未知问题 ID 单列诊断并隔离，不能进入正常分子。
2. 重复键不能重复计数；冲突内容默认隔离并标记不完整，不随意挑一个正确答案。完全相同的重复记录也需记录数量与明确去重规则。
3. 保留固定预期分母，缺失/未决项不得通过缩小分母抬高成绩。只有在语义成立时发布临时下界；正式成绩仍要求完整性通过。不能简单 clamp 到 1 掩盖计数问题。
4. `pass_at_1`、sample accuracy、first/any-success 等统计使用一致的有效样本集合，保留它们各自的定义；空数据集必须明确处理，不能除以零。

**CPU 验收：** n=2 却出现 rollout 0/1/2；负数/非整数索引；重复及冲突；缺失/未知 question；空集合。所有可发布比例在 [0,1]，异常仍使完整性失败；正常完整数据的既有指标与计数保持不变。

### A.7 Judge 成本和既有验证材料的口径

本节补充第 5.4 节，**不是新增 Judge 模型或 Prompt 优化任务**。

- B/C 固定 4 条耗时约 277.7 秒，8 次生成，其中 4 次复核，并发峰值 2；约 103,375 输入 token、13,404 输出 token。69.4 秒/回答是已经包含并发收益的墙钟摊销，外推时不能再除以 2。
- 当前正 Progress、零 Error、修复事件等均可能触发复核，4/4 复核符合现有规则。证据槽位限制没有限制全部 Thinking 长度，复核仍会再次输入轨迹；不能仅凭“压缩了证据”推断 token 成本大幅降低。
- 按这个小样本吞吐粗估，128/192 个未缓存回答约需 2.47/3.70 小时；这不是完整训练 batch 的实测或完工承诺。报告必须同时写出新回答数量、Teacher 缓存命中、复核率、token 数、实际并发、超时和样本长度，给出假设与区间。
- Teacher 成功标签可以跨 Warmup/GAD 复用；Student 新轨迹不能假定大面积命中缓存。成功标签缓存与 J1 的失败 journal 是不同机制，修复和成本统计都要分开。
- 6 小时 step deadline 只是容许等待，不是提速。正式训练与 health/preflight 读取同一最终 run 配置，不能混用测试 Judge 配置和冻结训练配置的不同 deadline。
- B/C 冻结配置还是 5k、78→156 预算，只用作修复证据；正式入口必须采用本文 17k 配置。既有真实 worker 检查没有覆盖完整 Ray/vLLM、多 rank FSDP 在线链路，仍须完成第 5.3 节的有限验证。
- 对 README 的累计 7 次 Critic 更新与 verification 的 6 次记录，核对原始日志并给出计数口径/勘误。若某次更新完成但尚未写入结果数组，应明确说明；不改写历史原始证据来凑齐数字。
- 现有 Progress 标签和梯度证据不能证明 Actor 提升，Student Error 的有效监督也尚未证明。保留这个研究限制，但不新增无限期质量校准门槛。

在线成本检查只沿用冻结 Judge，计入已有最多 4 个新回答、8 次生成（含复核/重试）、30 分钟边界。达到上限后记录未完成项及已观测成本，不自动延长。若成本仍不可接受，将减少复核、缩减标注范围等另列为**方法变更选项**交用户安排，不在工程修复中默认采用。

### A.10.2 N1：失效的 `unjudgeable` 不能绕过全局保护

**当前代码。** [process_v2.py](../rubric/core/process_v2.py) 中：

```python
unknown_math = any(e['type'] == 'unjudgeable'
                   for eid, e in events.items() if eid not in invalid)
```

`invalid` 包含 `event_spans_malformed`、`event_span_missing`、`event_schema_error` 等。一个 `unjudgeable` 事件如果证据写空 `{}`、写了不存在的 `s999` 或结构不合法，就会进入 `invalid`，从而被 `unknown_math` 排除。

**已复现。** 在 `event_record(progress=1, error=0)` 基础上加入：

```json
{"type": "unjudgeable",
 "supporting_span_ranges": {"r1": {"start": "s999", "end": "s999"}},
 "trajectory_claim": "cannot verify next step",
 "judge_verification": "cannot verify next step",
 "related_event_ids": []}
```

CPU 结果为：

```text
e2 reasons ['event_span_missing']
verified_progress: valid=True value=1
unresolved_error_severity: valid=True value=0
```

这直接违反 spec/prompt 的“unjudgeable 阻断全局 progress=1 与 error=0”，而且 prompt 明确允许空证据 `{}`，使该路径很现实。它和 R1 不同：R1 修的是 guard 分类，N1 修的是 parser 是否把“无法判断”的声明计入全局不确定性。

**修复要求。**

1. `unknown_math` 至少覆盖所有明确声明为 `unjudgeable` 的事件，不因证据定位失败而忽略；也可把 invalid unjudgeable 单独归入 `uncertain`，但必须阻断 `progress=1` 与 `error=0`。
2. 保留“invalid 事件不直接当数学证明”的原则，但“声明无法判断”本身必须影响全局标签，不能因为证据写坏而变成“没有不确定性”。
3. 审计字段记录 invalid unjudgeable 的 event ID、原因和是否触发 Mask；不能只在 `_event_issues` 里留痕。
4. 与 N7 一起决定空证据 `{}` 的语义，避免 prompt 让模型写一个 parser 必然判无效的事件。

**CPU 验收。** 覆盖：valid unjudgeable（已有测试）、invalid span 的 unjudgeable、空 `{}` 的 unjudgeable、unjudgeable + progress=1、unjudgeable + error=0、unjudgeable + 其他有效事件、neutral 对照。所有“声明无法判断”的案例都不能得到 progress=1 或 error=0；neutral 仍不阻断独立进展。不得用真实 Judge 作为验收前置。

### A.10.3 N2：GAD 完成签名必须绑定 Warmup handoff

**当前代码。** [pipeline.py](../gad/tools/pipeline.py) 的 `_stage_signature()` 对 GAD 只写：

```python
if stage == "gad":
    payload["warmup_manifest"] = None  # filled in by the caller once the handoff exists
```

当前全仓库没有调用方填这个字段；我在当前配置上检查，GAD 的 `payload["warmup_manifest"]` 就是 `None`。`check_skip()` 只比较 `stage_inputs_digest()`（含 `config_signature`）与 marker 里记录的 `total_steps`，不比较当前 `handoff_manifest.json`、Warmup checkpoint 内容或 step。

**影响。** 同一 run 目录里，如果 Warmup 被重跑、handoff 被替换，或从另一个 Warmup checkpoint 生成 GAD 初始化，GAD 的旧 `COMPLETED.json` 签名可以保持不变；`check_skip` 可能直接跳过 GAD，或按旧 `total_steps` 验收新计划。`recover_completed_stage()` 会读 `recorded_handoff`，但 marker 存在时走的是 `check_skip`，不经过该路径。

**修复要求。**

1. GAD 的 stage signature 必须包含：`handoff_manifest` 内容哈希、Warmup source step、handoff step、actor/critic HF 内容身份（或至少其清单/内容哈希）、handoff 生成时间不是必需但可审计。
2. `stage_inputs_digest()`/`check_skip()` 必须比较当前 plan 解析出的 handoff 与 marker 中的 handoff；不能用 marker 里旧的 `total_steps` 代替当前计划。
3. `check_skip` 与 `recover_completed_stage` 的行为要一致：要么都使用同一 handoff 身份，要么明确说明旧 marker 不兼容。
4. 旧 run 的 marker 没有 handoff 身份时，不能默认通过；应要求显式恢复/重新验证，不能仅因配置签名相同就跳过。

实现只补现有签名与检查，不另建阶段状态机。初次规划且 Warmup 尚未完成时允许 handoff 待定；在实际进入 GAD/判定已有 GAD 完成时解析其身份，不能在 SeqKD/Warmup 启动前强制要求未来产物。已有 GAD 目录发现来源冲突时明确停止并说明新 run/显式恢复方式，不能简单返回“不跳过”后自动覆盖原结果。

**CPU 验收。** 同一 handoff 正常跳过；不同 Warmup step/actor 内容不能命中旧 GAD marker，且不覆盖产物；首次 Warmup 尚未输出 handoff 时计划能正常生成，完成后可正常接入 GAD；marker 缺失的既有恢复、`resume`/`resume-complete` 按原语义执行。

### A.10.4 N3：阶段完成与恢复必须要求 extension checkpoint

**CPU 验收。** 完整 extension state 和合法 baseline 无 extension 必须通过；启用扩展却缺 `training_extensions/`、缺完整性 marker、manifest 内容不符或 cache snapshot 损坏必须阻断。不加载真实模型。该校验用于产物完成/恢复边界，不能在尚未写出 checkpoint 的训练启动阶段要求其已存在。

### A.10.6 N5：明确 `progress=1` 与 `error=unknown` 的语义

**当前代码。** [process_v2.py](../rubric/core/process_v2.py) 的 progress=1 分支只检查：

```python
if row['unresolved_error_severity']['valid'] and ... value == 1:
    mask(...)
```

不要求 error 维有效。CPU 构造 `progress=1, error.valid=false/value=null` 得到 `verified_progress valid=True value=1`。

**待定语义，不直接归为已确认 bug。** 当前 spec 要求两维分别判断，代码也已有 complete、analysis、unjudgeable、未知错误和未修复错误的检查。两种解释都可能在设计上成立：

- 如果 progress 和 error 完全独立，`progress=1` 只表示“可见推导完成”，error unknown 可以不阻断；
- 如果 progress=1 表示“充分解决且没有关键未修复错误”，error unknown 必须阻断。

当前 prompt 的“关键未知错误/修复不能通过省略事件来获得 0 或满 progress”要求阻断明确的数学不确定性，但不等同于“一切 error unknown 均说明 progress 证据无效”。本轮默认保留两维独立判断，先修 N1 的明确协议违反，并把 error 未决原因与 full-progress 证据分开测试。若完整解的证据不足，应按既有 full-progress 规则拒绝；不能只依据另一个维度的 `valid=false` 就新增一刀切 Mask。若确需把所有 error unknown 均设为阻断，单列为标签策略变更，说明覆盖率影响后由用户决定。N5 的完成条件是语义和测试明确，不是必须增加拒绝分支。

**CPU 验收。** `progress=1 + error=0`、`progress=1 + error=.5`、`progress=1 + error=1`、`progress=1 + error unknown`、`progress=1 + error invalid due invalid event`、`progress=.5 + error unknown`。按选定语义断言；若允许，报告中必须单列。

### A.10.8 N7：统一空证据 `{}` 的 prompt/parser 语义

[prompt v27](../rubric/prompts/judge_math_process_v27.txt) 和 [ONLINE_RUBRIC.md](../gad/ONLINE_RUBRIC.md) 都写“空证据 `{}`”，但 [evidence_ranges.expand](../rubric/core/evidence_ranges.py) 默认 `allow_empty=False`，事件空 `{}` 会 `event_spans_malformed`。CPU 复现：event 空 → `event_spans_malformed` → progress/error 被 Mask。

**要求。** 二选一，不能保留模糊状态：

- **禁止事件空证据：** prompt/doc 改成“事件至少一个区间”；parser 保持拒绝，并在 reason 中明确“event_requires_evidence”。此时 N1 仍需单独修复，因为 invalid unjudgeable 不能绕过。
- **允许受限空证据：** 只允许 `neutral`/`unjudgeable` 等不提供数学支持的事件为空，parser 对这种事件放行但不把它当作有效支持；同时 N1 必须阻断全局标签。不能对所有事件一律放行。

**CPU 验收。** 空事件 + neutral、空事件 + unjudgeable、空事件 + verified_progress、空事件 + explicit_error、空 label event_ids、正常单区间/多区间。按选定语义断言；若允许空 unjudgeable，必须同时验证它阻断 progress=1/error=0（N1）。

### A.10.9 N8：空 response 的可诊断处理

[critic_batch.py](../gad/extensions/critic_batch.py) 对空 `ids`：

```python
if not ids:
    raise ValueError("empty response cannot enter an extension critic update")
```

`last_response_logits` 也拒绝全零 response mask。spec/prompt 对空回答定义了 `progress=0`、`error=unknown` 的行为，但训练路径不是 Mask 或跳过，而是整步失败。

**要求。** 先区分“解码后文本为空”与“有效 response token 数为 0”。立即 EOS 可能仍有一个有效 token，不能仅凭文本为空推断 `last_response_logits` 无位置可取；应核对实际 rollout/mask 行为。

默认保留对真正全零 response mask 的明确失败，只在当前缺少诊断时补充 stage、step、role、样本 ID 和原因。若它本就是 backend 不支持的输入，不要求实现自动跳过或补 token；错误应在 optimizer 更新前传播，不能只让一个 rank 自行继续。正常的仅 EOS/特殊 token 回答按既有路径处理，不扩大拒绝范围。

只有实际证明正式 rollout 会产生必须支持的零 token 样本，才另行设计处理；不能简单删 pair 或仅 Mask 辅助 loss，因为 BT 前向、Actor 批、DP 整除和全局归一化仍可能失败。该设计不作为本轮默认的额外框架改造。

**CPU 验收。** 空 student/teacher 的有效 mask、仅特殊 token、正常最短回答、全零 mask；确认合法最短回答通过，非法输入在更新前明确失败。若 backend 保证有效 token 非空，记录证据与限制即可，不为了假设场景增加恢复分支。

### A.10.10 N9：评估使用实际 expected question ID 集合

**CPU 验收。** 连续 ID；非连续 `global_index`；子集 `max_prompts`；rollout 0/1/2；重复/冲突/缺失/未知；空集合。所有可发布比例在 [0,1]，异常使完整性失败；正常完整数据的指标与现有定义一致。

### B.2 E4：评估身份应覆盖实际加载的 HF 内容

### B.5 性能补验的共同条件与候选顺序

沿用 [benchmark_train.py](../gad/tools/benchmark_train.py) 和现有候选 YAML，不新建训练器。所有候选从**同一源 run、同一已完成 checkpoint、同一数据位置、同一源配置**恢复，使用同一修订 backend 和目标四卡拓扑；源 run/数据只读，输出使用新目录。

| 顺序 | 拟测设置 | 对照目的与边界 |
|---|---|---|
| B0 控制 | 当前保守配置，offload/checkpointing 保持开启、microbatch=1、eager=true | 用同一工具得到完整控制；旧 428.8 秒不能代替这次控制 |
| B1 生成侧 | 在 B0 上仅设 `rollout.enforce_eager=false` | 检查当前 vLLM/backend 是否支持图捕获及 sleep/wake/权重同步；是候选，不保证提速。失败保留原因，不修改 vLLM 内核或升级依赖来强行跑通 |
| B2 Critic | 在 B0 上只将 Critic microbatch 1→2 | 测 Critic 调度/更新开销，不以 resident 已获收益为前提。核对 dynamic-batch 当前值与实际生效路径，不悄悄合并 token budget/动态 batching 改动 |

### B.6 观测步数、预算与停止条件

**后续拟安排一次最多 180 分钟的性能补验窗口**，包括启动、权重/状态加载、图捕获、失败清理、保存和可选复核。本条用于制定下一次执行范围，本轮不实际启动；用户此前中断的运行保持停止，不能在后台自动续跑。Judge 保持暂停，不占用其卡或复用其服务。

1. B0/B1/B2 每项默认 **4 个训练步：1 步预热 + 至少 2 个无验证/无保存的正常观测步 + 1 个保存退出步**。现有工具 `--steps` 包含末步保存，原 3 步设置实际只留下 1 个正常观测步，不能再报告成“两步正常对照”。选择不跨常规保存/评估点、且不超过原训练总目标的源 checkpoint；如果实际正常步不足，标记未完成，不用保存步补数。
   对应现有工具 `--steps 4 --warmup-steps 1`。若使用已完成的 `global_step_500`，则 501 为预热、502/503 为正常观测、504 为保存退出；501 不能列为稳态样本。500 是已有证据支持的候选位置，不硬编码为所有新实验的恢复点；最终源位置需满足本条条件，并让所有候选一致。
2. 先完成三项初筛；如有余量，优先复核最有依据的候选，而非新增多个开关。复核可安排 1 步预热 + 3 个正常步 + 1 个保存退出步，仍计入同一 180 分钟。时间不足时明确“仅初筛，尚未复测”，不自动扩展窗口。
3. 启动前给出各项预计时间和剩余预算。按当前约 7–8 分钟/GAD 步，三项共 12 步已约需 84–96 分钟，另有初始化和保存等开销；不能把小模型短链路的 11.76 分钟当作本次预算依据。剩余时间不足时停止启动下一项，列出未测原因。
4. 一项 OOM/不兼容后保留退出码及诊断；可在剩余预算内用已列的下一候选替代，不搜索无限回退组合。不能把用户主动终止当成 OOM；未正常退出、未完成保存或缺关键显存记录的结果保留为探索性观测。
5. 常规性能测试不同时争抢训练 GPU；仅清理本次自有进程，不执行影响其他任务的全局 Ray/GPU 清理。不得因观察不到提速改动算法、训练阶段交接或恢复语义。

第 5.3 节的四卡正确性链路已经验收，不再额外安排完整 60 分钟重测。只有本轮改动真正触及未覆盖的运行路径，才在上述剩余窗口内做最小针对性检查；不能把每个性能候选都重新跑一遍 SeqKD/Warmup/GAD。

### B.7 如何判断“值得采用”

每项交付一行可比较的摘要，并附原日志，而不是仅给一个平均秒数：

- 完成状态、实际有效开关、正常步数量、每步时间及其中位数；初始化/图捕获、保存时间单列。
- 实际 prompt 数、生成 token 总量、生成 token/s、输出长度和截断率；`gen` 与 `generate_sequences` 等嵌套计时分开解释，不相加。输出更短导致 wall time 变小，不能直接归因为内核提速。
- Critic/Actor 更新、Reference、同步与 sleep/wake 的已有分段计时；缺少关键项时只在已有边界补计时，不加入全面 profiler 改造。
- 每卡观测显存峰值、采样间隔及其限制，长 Teacher/Student、8192 附近轨迹的实际覆盖。不能用某一时刻显存低证明常驻方案安全。
- 源 checkpoint/数据状态、backend、配置差异和恢复结果；退出正常且保存完整。若正常步数太少或波动大，不宣称稳定 P90、统计显著或整轮必不 OOM。

小于波动范围的收益记为“未确认”，不用任意 1–2 秒差异选胜者。只有可比工作量下总体耗时和相关阶段指标共同支持、且运行正常时，才给出“短测支持的候选”；未复测的候选不直接覆盖默认机器配置。若多项均无明确收益，可以保留现配置，但必须说明哪些已测、哪些仍未测，不能将其表述为“所有超参数都已优化”。

先在 GAD 筛选；有依据的最终候选若要同时用于 Warmup/correctness-only，需在同一剩余预算内做相应最小兼容/显存确认，否则明确推荐只适用于已测阶段和方法。Judge 等待完全是另一项成本，不把这些训练端收益外推成 joint 总耗时等比例降低。

### D.1 N3：首次交接不能成为不完整 GAD checkpoint 的退路

**已确认路径。** `resolve_gad_resume()` 在“最新 step 等于记录的 handoff step”时，先只检查 actor/critic/data 文件，随后直接返回 `mode=handoff`，绕过后面的 `extensions_required=True`。在抽取当前函数、模拟文件校验返回成功的 CPU 夹具中，即便启用 rubric 且没有 `handoff_initialization.json`，也返回 handoff，完整 extension 检查没有被调用。该证据验证分支问题，不是实际 FSDP 恢复测试。

**最小修复：**

1. 仅在启用 rubric/replay 的 GAD 恢复路径，允许已明确证明是首次 Warmup 初始化的 checkpoint 进入 fresh-optimizer handoff 分支。复用现有 `handoff_initialization.json`，核对其 source、step、`same_stage_resume=false` 与现有 handoff 记录一致；不是仅检查同名空文件存在。
2. 已形成 GAD extension checkpoint 的产物按同阶段恢复处理，不能因步号相同或遗留初始化标记而重置 optimizer。缺状态、损坏标记或 manifest 引用缺失按现有完整性边界报错，不静默退回 fresh handoff。
3. 合法首次 Warmup→GAD 交接本来就没有 GAD extension 状态，仍应正常启动。没有启用扩展的 baseline 保持既有路径；只在判别这两种状态的位置补条件，不新建恢复系统。

**定向 CPU 验收：** 无 marker 的 handoff-step 伪完整产物；marker 与来源/step 不符；合法首次交接；合法同阶段 extension 恢复；已有 extension 状态但残留初始化标记；baseline 正常交接。检查恢复模式、起始步和 optimizer 策略，不只检查是否抛错。复用既有 helper/夹具，不为本项再跑完整 GPU 链路。

### D.2 N4：配置声明必须与实际 spec 一致

当前只有 `rubric.version=math_process_v2` 才进入 spec 协议检查；改成 `math_v1` 并配合 legacy scorer，可绕过该分支。本次以真实 `compose_config()` / `validate_config()` 构造对应配置，正常 v2.7 与混搭配置均返回空错误列表。统一 scorer 的正式配置已有另一层拒绝，因此不能说当前正常 v2.7 配置全部失效；问题是仍允许构造混搭配置。

在启用 rubric 时读取一次 spec，先检查 `spec.version == rubric.version`；v2 再检查当前 schema/input protocol 及 prompt 的显式协议声明。缺文件、坏 YAML、非映射 spec 给出启动前错误，不发 Judge 请求。仅保留已有合法旧配置，不增加自动版本推断、转换或多版本框架。

验收包含当前 v2.7、已有合法 math_v1、旧 v2.6 spec、version 混搭、input protocol 不匹配和坏 spec。**prompt 缺少显式版本声明不自动等于非法**：当前实现允许历史 prompt 无声明；本项不偷偷新增“所有 prompt 必须有版本头”的门槛，有声明则必须匹配。

### D.3 N10：干净目录测试不能借用本机模型和历史报告

`test_appendix_bc.py`、`test_thinking_judge.py` 读取外部 `model/Qwen/Qwen3-8B` / `Qwen3-14B`；后者还读取 `reports/rubric_v2/thinking_judge_20261015` 的样本和旧 completion。这些文件未必随发布包存在。仅替换绝对路径字符串仍不能解决迁移问题。

1. 普通 CPU 逻辑测试使用临时或仓库内小型 tokenizer/事件/响应夹具，覆盖原来的解析与配置行为。历史 completion 如确有必要，提取最小且可审阅的固定样本至测试夹具目录，不将整个 reports 加入运行依赖。
2. 必须验证真实 Qwen tokenizer、reasoning parser 或 xgrammar 兼容性的测试，保留为显式环境变量控制的可选集成测试。无对应资产时清楚报告未执行/skip，不能用 mock 成功冒充真实模型兼容。
3. 测试迁入发布包时一并检查旧 override 和动态引用；若裁剪历史实验脚本，保留其仍有价值的回归覆盖，不靠保留所有废弃脚本解决测试依赖。
4. `40 套件 / 386 项 / 0 skip` 是此前本机记录，不是新交付必须原样维持的数量。新增或拆分用例后报告真实数量：必要 CPU 集合全部执行通过，可选集成集合单列执行/跳过及原因。不能一边要求无模型时 skip，一边要求总计 0 skip；也不能把必要失败用例改成 skip。

### D.4 不新增策略变更的三项澄清

**S1：保留 unresolved 优先于丢弃的语义。** `correct-nontruncated` 第一轮先排除截断候选，再判正确性。所以出现 unresolved，指的是至少一条**未截断且尚未评分成功**的候选。另有一条“正确但截断”的回答，仍不能证明前者不合格；直接返回 `None, correct_but_truncated` 会丢弃整个题目。提纲所说“候选先后顺序导致误判”也不准确，交换二者顺序当前仍得到 unresolved。

本次 CPU 夹具直接调用抽取的现有选择函数，结果如下（`select=all` 另据源码确认）：

| 候选组合 | 应保留的行为 |
|---|---|
| 未截断、评分超时 + 正确但截断（两种顺序） | `UnresolvedCandidates`，不能据此丢题 |
| 未截断且明确错误 + 正确但截断 | `correct_but_truncated` |
| 前面评分失败，后面正确且未截断 | 选择后面合格候选 |
| `select=all` | 既有不过滤语义不变 |

只补上述语义回归，不修改 Teacher 数据、不重新采样，不将“减少报错”当作标签修复。若以后希望跳过评分服务失败的题目，应作为明确的数据策略变更另议。

**J1：固定为同 stage、协议/请求身份、训练 step 内跨重启累计。** 同一步重启不能把 attempt 清零；新训练步有自己的尝试预算，成功结果仍可按已有缓存身份复用。这与全 run 累计成本统计是不同事情。沿用当前 step journal 和提交状态未知时默认 abort 的规则，不提升为全 run 失败请求封禁表，不另建全局 ledger。补同 step 恢复到上限、跨 step 新预算及未知提交不自动重发的夹具。

**A.6/N5：沿用现有定义。** 完全相同的重复记录不重复计分，但仍标记 incomplete；内容冲突继续隔离，预期分母固定。无需新增去重开关，也不让该评估完整性状态再次阻断已经合法完成的训练阶段交接。N5 继续保留 progress/error 两维独立及已约定的 unknown 处理，不重新发起策略审批，不把本次工程修复变成新的标签定义。
