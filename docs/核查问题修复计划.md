## 0. 结论摘要

工程骨架经过检查是自洽的，不需要重构：

- 四通道 critic（`adv` + 三个辅助头）的前向、BT+辅助 loss 接线、跨 DP 归一化与按 response 去重、
  mask 传递、标签缓存、checkpoint 事务——逻辑一致，且被 `test_microbatch_equivalence` 的梯度等价校验覆盖。
- 6 个工程补丁的锚点在 seqkd / warmup / gad 三个 stage 上**都恰好匹配一次**；重新打补丁得到的树与
  已部署的 `gad/.backends/{seqkd,warmup,gad}` 逐字节一致。
- parser 的健壮性良好：5000 次随机 JSON 嵌套变异 0 未捕获异常，3-cycle 正确失效，重复 key、span
  存在性、枚举、`removable`/`repaired`/`uncertain_repair` 分支都符合其测试声明。

问题集中在四处，按对训练信号的影响排序：

| 组 | 问题 | 对训练/评估的影响 |
|---|---|---|
| A | 答案抽取器把格式变体判错，且给出 `valid=True` 的标签 | **直接向 critic 灌入错误标签** |
| B | judge 证据校验仍可被语义错误的标签绕过 | 假 judge 输出能进 loss |
| C | 评估/配置管道 8 个真实缺陷 | "评估通过"不可信；部分 stage 无法运行或 resume |
| D | 测试套件漏掉全部 rubric/V2 测试、文档与实际不一致 | 回归风险不可见 |

**执行前提**：A 组改动会改变 `scoring/math.py`，因此改变 scorer fingerprint，进而使所有既有标签缓存失效

## 2. A 组：答案抽取器（[scoring/math.py](../scoring/math.py)）

这一组是本次核查中唯一"会直接污染 critic 训练目标"的问题，优先处理。

### A1 列表/引用前缀的 `Answer:` 行完全解析失败并被当成有效错误

**现状**：`MARKER`（[math.py:25](../scoring/math.py#L25)）锚定 `^[ \t]*(?:\#{1,6}[ \t]+)?`，只接受 `#` 前缀；
`-`/`*`/`+`/`>`/`1.` 都不匹配 → `parse_status='no_answer'` → `correctness_label`（[math.py:233](../scoring/math.py#L233)）
返回 `{'value': 0, 'valid': True}`。

已复现：

```
'- Answer: 2'        parse=no_answer  label=0/True      （数学上正确）
'> Answer: 42'       parse=no_answer  label=0/True
'1. **Answer:** 42'  parse=no_answer  label=0/True
'* **Answer:** 42'   parse=no_answer  label=0/True
```

并且已确认它**以 mask=1 进入 critic 目标**（用真实 `OnlineRubric.annotate` 复现）：

```
student response : '- We subtract 3: 2x=4\n- Answer: 2'
targets [corr, prog, err]: [[0.0, 0.5, 0.0]]
masks                    : [[1.0, 1.0, 1.0]]      ← corr 的 mask=1，即"该标签可信"
```

对照旧 CARD scorer（`sample/math_scorer.py`），`- Answer: 2` 与 `> Answer: 42` 都判 `True`——
所以这是**新 scorer 引入的回归**，不是口径演进。同时 `parse_failure_rate` 只统计 `malformed`/`ambiguous`，
这类伪负例在指标中不可见。

**修复**：在 `MARKER` 的行首前缀部分加入列表/引用/序号前缀，例如
`^[ \t]*(?:(?:[-*+])[ \t]+|\d{1,3}[.)][ \t]+|>[ \t]*|\#{1,6}[ \t]+)*`。
注意保持对 `> ` 多级引用（`> > Answer:`）的容忍。

**验收**：上表四行全部变为 `parse=ok` 且 `correct=True`；新增回归用例覆盖 `-`/`*`/`+`/`>`/`1.`/`1)`/多级引用。

### A2 空白折叠制造假正确

**现状**：[math.py:176](../scoring/math.py#L176) 的 `canonical = re.sub(r'\s+', '', s)` 把分开的数字串合并。

已复现：

```
_grade('1 2', '12')     = True
_grade('1 2 3', '123')  = True
score('Answer: 1 2','12') -> correct=True, label={value:1, valid:True}
```

**修复**：不要无条件删除空白。只在单位/运算符两侧去空白，或在折叠前先按 token 序列比较；
两条路径都要保证不把两个数字组粘连。

**验收**：`_grade('1 2','12')` 为 `False`；`_grade('5 cm','5cm')`、`_grade('2 x','2x')` 仍为 `True`。

### A3 `**42**` 这类加粗值被判为 grader error

**现状**：`MARKER` 结尾的 `(?:\*\*|__)?` 消费掉值的**起始** `**`，而 `_clean`（[math.py:42-47](../scoring/math.py#L42-L47)）
只剥离对称包裹。

已复现：

```
'Answer: **42**'        pred='42**'  parse=ok  grade=error  label={value:None, valid:False}
'Answer: __42__'        pred='42__'  parse=ok  grade=error  label={value:None, valid:False}
'Final Answer: **42**'  pred='42**'  parse=ok  grade=error  label={value:None, valid:False}
```

**修复**：在 `_clean` 中额外剥离单侧的尾部 `**`/`__` run（或不在 `MARKER` 消费冒号后的加粗，改为在 `_clean` 统一去包裹）。

**验收**：上述三例 `pred='42'`、`correct=True`；同时 `_clean('**42')`、`_clean('42**')` 都得 `'42'`。

### A4 "取最后一个 marker"缺少"这是不是一个答案"的门槛

**现状**：[math.py:84](../scoring/math.py#L84) 按位置取最后一个候选，没有值形态检查。

已复现：

```
'Answer: 42\n\nFormat note:\nAnswer: <the number>'  → pred='<the number>' → label=0/True（正确答案被判错）
'Answer: 42\n\nThus ... Answer: $Answer where ...'  → 抛错 → label=None/False（同样输入，处理不一致）
```

**修复**：选定候选后要求其值形如单个数学对象；若选中的值是散文/占位符，返回 `parse_status='malformed'`
（或回退到最后一个"像答案"的候选）。

**验收**：第一例不再产生 `value=0, valid=True`；两例的处理方式一致（同为 malformed 或同为正确）。

### A5 未闭合的 `\boxed{` 遮蔽后续 box

**现状**：`_unbox`（[math.py:39](../scoring/math.py#L39)）在畸形时返回 `end=len(text)`，`extract_answer`
（[math.py:54](../scoring/math.py#L54)）据此跳过位于该"盒子"内的所有后续 box。

已复现：

```
extract_answer('We tried \\boxed{ here.\nFinal Answer: \\boxed{42 cm}')
  → pred='\\boxed{42 cm}', parse=ok, 但 grade=incorrect
```

**修复**：只在被包含的 box 解析状态为 `ok` 时才跳过其中的 box；畸形时返回 `end=start+len('\\boxed{')`
（或 `start`），不覆盖后文。

**验收**：上例重新按 `42 cm` 正常判等；`extract_answer('\\boxed{ oops\nAnswer: \\boxed{1} and \\boxed{2}')`
返回 `ambiguous` 而不是把字面文本当答案。

### A6 指标与训练对"解析失败"的判定不一致

**现状**：`correctness_label`（[math.py:236](../scoring/math.py#L236)）把解析失败 mask 掉，但
`evaluation_value`（[math.py:239](../scoring/math.py#L239)）/`compute_score`（[math.py:243](../scoring/math.py#L243)）
把 invalid 映射为 `acc=0`/`score=-1`，`evaluate/rescore.py:27,36` 用它计算 `sample_accuracy`。

**修复**：让"非 correct/incorrect"的行不进入准确率分母，或把 invalid 状态向上传播；指标与训练口径必须一致。

**验收**：同一失败样本在 `correctness_label` 与 `evaluation_value` 下的"是否计分"决策一致，并有断言。

### A7（低优先，当前不可达）单位/角度与 LaTeX 编码差异

`quantity_` 结构化 key 使用字面单位文本（[math.py:133-134](../scoring/math.py#L133-L134)），
导致 `42\text{ cm}` 与 `42 cm`、`90^\circ` 与 `90^{\circ}` 判为不等；
`_parse_latex` 丢括号后 `\pi→pi` 会把 `i\pi` 粘成 `ipi`（[vendor/oprd_math.py:325-340](../scoring/vendor/oprd_math.py)），
使 `e^{i\pi}` 触发名称检查失败。

已确认当前 5k 与 17k 的 ground truth **全部是纯整数**（0 条含反斜杠或 `/`），所以此条**当前不可达**。
修复应在换数据集之前完成：在构造结构 key 时归一化 `\text{X}→X`、`^{\circ}`/`^\circ`→`\circ`，
并在 π 替换前插入乘号。

## 3. B 组：judge 证据校验（[rubric/core/process_v2.py](../rubric/core/process_v2.py)）

### B1 `corrected_error` 可以引用"错误本身"那个片段，伪造修复

**现状**：[process_v2.py:168](../rubric/core/process_v2.py#L168) 只要求 `corrected_error` 链到**某个**
`explicit_error`，不要求修复片段与错误片段不同。

已复现（响应 `2x=4\n\nx=3`，`e3=corrected_error(span=s2)` 即错误行本身，reason 写"judge 在脑子里改好了"）：

```
error label value=0 valid=True   violations=[]
```

这与 [spec:18](../rubric/specs/math_process_v2.yaml) 和 [prompt:10](../rubric/prompts/judge_math_process_v2.txt)
的"judge 自己算出的答案不能代替原文证据"直接矛盾。

**修复（建议，需你确认判据）**：要求 `corrected_error` 的 `span_id` 与被引用的 `explicit_error` 的
`span_id` 不同；更严格的做法是要求原文中存在替换值。若只做前者，要在 spec 中明确说明"仅排除最直接的伪造"。

**验收**：上述构造被 mask，且原因进入 `_mask_reasons`；真实修复样例（替代值与代入检验都在原文）不受影响。

### B2 有效的 `unjudgeable` 事件不阻止满分/零错

**现状**：[process_v2.py:239](../rubric/core/process_v2.py#L239)/[:244](../rubric/core/process_v2.py#L244) 只检查**无效**事件
（`uncertain_error`）。

已复现（一条 `verified_progress` + 一条**有效** `unjudgeable`）：

```
progress=1/True  error=0/True  violations=[]
```

与 [spec:27](../rubric/specs/math_process_v2.yaml) "未知错误或修复不能支持全局完成与无错判断"矛盾。

**修复**：存在有效 `unjudgeable`（或 `neutral`）事件时，阻断 `progress=1` 与 `error=0`；
或在 spec 中把这条承诺降级。

**验收**：上述构造中 `progress` 不再为 1、`error` 不再为 0；`neutral` 辅助事件仍不清空独立的 `progress=.5`。

### B3 括号题反例仍然通过全部校验（确认，无法在 parser 层修复）

已复现（与你文档 §9.1 完全一致）：

```
resp='We compute 1+2*3+4*5+6.\nAnswer: 721\n'
e1=verified_progress(span=s1, reason='correctly found 77, fixing the earlier error')
progress=1/True  error=0/True  violations=[]
```

**这不是接线缺陷**：parser 结构上无法判断"片段是否支持该断言"。可选处理：

1. **（推荐）** 在 spec 中显式声明 parser 只保证结构一致，不保证`片段支持判断`；
   把该承诺移交语义校验（span 条件下的蕴含检查或第二个 judge）；
2. 把"自算答案归属"列入人工校准门槛，而不是继续加长 prompt。

**不要**为了这条继续叠加正则或让 parser 冒充数学判断器。

### B4 分类与记账问题

- [online_v2.py:145](../gad/extensions/online_v2.py#L145) 把**合同违规**（数学/证据被拒）归入
  `process_unavailable_kind='technical'`。这会让 §10.4 的零覆盖保护把"judge 持续产出非法标签"误报为"服务故障"。
  建议新增一类（如 `contract_rejected`），并让阈值统计与质量报告使用它。
- [process_v2.py:211](../rubric/core/process_v2.py#L211) 的 `mask()` 用**原始** `row[dimension]['valid']` 做守卫，
  而不是 `labels[dimension]['valid']`，导致已被拒的标签又被全局规则重复检查，把无关原因堆进 `_mask_reasons`。
- [process_v2.py:213](../rubric/core/process_v2.py#L213) 的 `contract_violation` 被**最后**一个原因覆盖；
  审计工具（`online_v2.py:50`、`calibrate_*`）读这个字段，会误判 mask 的真实成因。建议保留首个原因或记录全部。
- 三个 `mask_reasons` 名称与实际条件不符：`full_progress_requires_complete_analysis` 在 `completion != 'complete'`
  时也触发；`zero_error_requires_checked_math` 与 `full_progress_has_unresolved_error_evidence` 实际由
  `uncertain_error`（无效错误证据）触发。建议改名，避免误导后续审计。
- [process_v2.py:238](../rubric/core/process_v2.py#L238) `progress, error = labels.values()` 是死代码，可删。
- `verify` 侧：[heads.py:46](../rubric/core/heads.py#L46)、[process_v2.py:107](../rubric/core/process_v2.py#L107)
  硬编码"4 个头"，与 `len(LAYOUT)` 解耦。建议统一为 `layout_for()` 派生。

### B5 grammar 无法表达"修复必须链接"（小）

`JUDGE_SCHEMA_V2`（[process_v2.py:97-108](../rubric/core/process_v2.py#L97-L108)）无法表达"`corrected_error` 至少链接一个
`explicit_error`"，所以 xgrammar 会生成 `related_event_ids: []`，随后被 parser 必然拒绝，浪费一个事件槽位。
建议像 `LABEL` 那样按类型分 `anyOf` 分支，为 `corrected_error` 加 `minItems:1`。

### C7 每 stage 的 `rollout.n` 覆盖是死配置

**现状**：[stage_rollout_n](../gad/tools/pipeline.py#L249-L263)（pipeline.py:249-263）读

已复现：

```

warmup for_stage rollout.n=8  n_warmup=1 -> stage_rollout_n=1   ← 意图 n=8 被丢弃

**修复**：让 `stage_rollout_n` 在对应 `n_<stage>` 未显式设置时采用 `for_stage(stage).get("rollout.n")`；
否则删除这个无效覆盖以免误解。

### C8 `rollout.n` 类型未校验导致配置校验崩溃

```
