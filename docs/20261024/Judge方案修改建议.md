# Judge 方案修改建议

日期：2026-10-25
状态：建议，尚未实施。本文是对 [Judge 单轮简化与训练验证方案](../20261024/Judge单轮简化与训练验证方案.md)（下称"原方案"）的补充，不取代原方案。原方案中已确定的取舍和"限制过度修改"的原则继续有效；本文只增加一项前置诊断，并对原方案的若干步骤提出修改。

## 1. 背景：为什么需要补充

依据来自 [17k 进展汇报](../17k实验与工程进展汇报_20261023.md) 的正文"补充一"和 10 月 25 日附加项，计算脚本和完整输出见 `reports/eval_length_20261025/`（`reports/` 不进入 Git）。与 Judge 相关的结论有三点：

1. **截断已不是首要矛盾。**8k 下被截断的回答主要集中在难题上。放宽到 16k 后，超过 8k 的回答最终只有 4–9% 答对；cnt 数据把 GAD 的评测截断从 54.6% 降到 31.7%，各难度档的正确率却基本不变。这为回到 Judge 实验提供了理由。
2. **correctness-only 没有带来可分辨的提升。**8k 下 correctness-only GAD − baseline GAD 为 −0.14pp（95% 区间 [−1.84, +1.55]）；16k 下为 +1.11pp（[−0.61, +2.91]）。仅重新采样一次，同一模型的四任务平均就会变化 0.5–0.8pp。
3. **当前评测的分辨率约为 1.5–2pp。**AIME 只有 30 题，却占四任务等权平均的一半；每个方法只有一个 seed。

第 2 点是本文的出发点：correctness 监督和过程监督走的是**同一条通路**。如果这条通路本身传不到 Actor，那么 Judge 标签做得再好，也很难改变 Actor 的分数。

## 2. 建议一（前置诊断）：辅助监督是否改变了 Critic 对同题回答的排序

### 2.1 原因

- 过程标签只进入 Critic 的辅助头，Actor 奖励仍为 `reward_source: adv_only`。
- GAD 每题只采 2 条学生回答（`rollout.n=2`），GRPO 按组内标准差归一化，所以优势恒为 ±0.707（同分时为 0）。Actor 实际得到的信号只有一个：**Critic 的对抗分数认为两条回答中哪条更好**。
- 因此，辅助监督要影响 Actor，必须通过共享主干改变对抗分数对同题两条回答的排序。原方案第 7 节第四步把"讨论奖励通路"放在正式训练无收益之后；本文建议提前到实现之前或与实现并行，因为它只需要前向计算。

### 2.2 做法

只做推理，不训练，不修改任何已有 run。

- **Critic：**
  - baseline：`runs/baseline_06b_17k/gad/global_step_542/critic`
  - correctness-only：`runs/correctness_06b_17k_20261021/gad/global_step_542/critic`（带 `rubric_head_layout`，含辅助头）
  - 可选：`runs/baseline_06b_17kcnt/gad/global_step_424/critic`（cnt 数据，作为参照）
  - 均为 FSDP 分片（world size 4），需要先用仓库已有工具（`gad/tools/model_merge.py` / `merge_model2hf.py`）合并到单独目录，不写回原 checkpoint 目录。
- **打分方式：**复用训练中计算对抗分数的代码路径（`ray_trainer.py` 中 `critic_wg.compute_values` 及其后取 response-level 分数的逻辑），只取对抗通道，不自行重写打分规则。输入格式必须与训练时一致（DAPO 提示词、chat template、`enable_thinking=False`）。
- **回答对：**从已有 8k 评测样本中取"同一道题、一条答对、一条答错"的回答对：
  - 来源：`runs/baseline_06b_17k/evaluation/math_unified_v1_n8_math500n2_8k/gad/*/generation/raw_samples.jsonl` 和 `runs/correctness_06b_17k_20261021/evaluation/math_evalfix3_n8_math500n2_8k/gad/*/generation/raw_samples.jsonl`。
  - 对错标签使用合并后的评分器结果（旧 baseline 用 `eval_fix/outputs/2026-10-23.stage-b-merged/baseline_17k/per_sample.jsonl`；correctness-only 用各任务 `scores/scored_samples.jsonl`）。评分器未决的样本不进入回答对。
  - 两个 Critic 必须对**同一批**回答对打分。
- **指标：**
  - 主指标：Critic 给答对回答更高分的比例（同分记 0.5），按题目做配对 bootstrap，报告差值和 95% 区间。
  - 分层报告：
    - 两条都正常结束（`finish_reason=stop`）的回答对。这一层衡量 Critic 是否能区分推理对错，是关键结果。
    - 答错的一条被截断的回答对。这一层 Critic 可能只靠"是否写完"就能区分，作为参照。
  - 按任务分别报告回答对数量；AIME 回答对很少，只作参考。

### 2.3 结果如何使用

| 结果 | 含义 | 后续 |
| --- | --- | --- |
| correctness-only 的 Critic 在"两条都写完"一层明显更好 | 辅助监督能经共享主干改变对抗分数的排序 | 过程标签值得投入，按原方案推进 |
| 两者相近 | 辅助监督基本没有传到 Actor 能看到的信号 | 先讨论奖励通路，例如让辅助头分数进入 Actor 奖励，或增加每题采样数；再决定是否继续投入 Judge |
| 只在"截断"一层有差别 | Critic 学到的主要是"是否写完" | 同上，并注意过程标签在截断回答上的作用 |

诊断结果不阻塞第 3 节第 1 项的实现工作，但应在正式实验前得出。

## 3. 建议二：对原方案的修改

### 3.1 事先估算成本，并设定可接受上限

- 粗略估计：旧双轮协议每次调用输出中位数约 1670 tokens，其中思考约 770、JSON 约 710；单请求生成速度约 28 tokens/秒。direct_v1 去掉长 JSON 后，每次调用约 1000 tokens，约 35–40 秒。
- 并发 2 时，每步 16 条约需 5 分钟。Warmup 212 步加 GAD 212 步，如果标注阻塞训练步，约额外增加 35 小时；训练本身每步约 6 分钟，相当于总耗时接近翻倍。
- 上述数据来自暂停的 `rubric_joint_06b_17k_20261021` 在 Warmup 第 1 步的记录，当时学生回答很短；后期学生回答更长，实际成本会更高。
- **建议：**正式实验前设定上限，例如"每步额外耗时不超过训练本身耗时的 50%"。超出时按原方案第 5.2 节只比较一次每批 8 条。

### 3.2 固定 32 条测试加入一个并发档位

- 并发只是 Judge 服务的参数，不改变协议和标签含义，但它决定完整实验能否在可接受的时间内完成。
- 旧分析的显存估算（Qwen3-8B 两卡张量并行，每卡约 10GB 可用于 KV cache）表明并发 8 可能可行，但需要实测。
- **建议：**同一批 32 条分别以并发 2 和并发 8 各运行一次，报告总吞吐、单请求中位数和 P95 延迟，以及是否出现显存不足。
- 这会使原方案第 7 节第二步的生成预算从 40 次放宽到约 64 次（32 × 2）。墙钟上限按两次运行分别计算。**这一放宽需要用户确认后才能执行。**
- 同时确认标注在训练中是阻塞训练步，还是与 rollout 生成重叠。这决定 3.1 节的估算是否成立。

### 3.3 检查过程标签是否只是答案正确性的重复

- Judge 能看到标准答案，而"进展=1"的含义是"整题已解决"，它很可能与答案正确几乎重合。
- **建议：**在固定 32 条和短训练探针中都报告：
  - "进展标签（0 / 0.5 / 1 / null）× 答案是否正确"的交叉表；
  - "错误标签（0 / 0.5 / 1 / null）× 答案是否正确"的交叉表；
  - 按"是否截断"拆分的两个标签分布。
- 判读：
  - 如果"进展=1"与"答案正确"的重合超过约 90%，过程监督新增的信息主要在"进展=0.5"和错误维上，后续分析应集中在这两处。
  - 如果截断的学生回答几乎都被标为"进展=0.5、错误=0"，这部分标签的信息量有限，需要在报告中说明。
- 这些只用于说明标签的信息量，不作为通过或停止的门槛，也不据此修改协议，符合原方案第 8 节的约束。

### 3.4 固定样本使用 cnt 的真实回答

- 原方案第 7 节第二步已允许用 cnt 数据实验的后期学生回答替换最多 8 条真实样本。`baseline_06b_17kcnt` 已训练结束，具备条件。
- **建议：**从 cnt GAD 后期（第 400–424 步）的学生 rollout 或其 8k 评测样本中选 8 条替换，截断与正常结束的都要包含，保留来源清单后冻结。

### 3.5 正式比较前确定训练数据

- 实现与 CPU 回归、固定 32 条、Warmup → GAD 探针三步都与训练数据无关，可以先做。
- 正式比较的数据目前有两种可能：
  - **沿用 `dapo_math_17k_v2_cnt`：**baseline 已有；还缺 cnt 上的 correctness-only 对照，需要补跑。
  - **改用 API 重新生成的数据：**baseline、correctness-only 和 direct joint 三组都要在新数据上重跑。新 teacher 会改变回答风格，不能与旧 baseline 直接比较。
- API 数据建议先做小规模试点：从 cnt 剔除的 3,777 道题中抽 200–300 道，统计新 teacher 在 8k 内的正确率和回答长度，再决定是否全量生成。如果新 teacher 只有写到 8k 以上才能解出，这些题在训练时会再次被截断或剔除。
- 数据由用户决定，执行模型不自行选择。

### 3.6 事先确定正式比较的口径和成功标准

- **任务集合：**
  - 主指标：AIME24、AIME25、AMC23、MATH-500，加上 Minerva、OlympiadBench、MMLU-Pro-Math（扩展评测见 `evaluate/EXTENDED_EVALUATION.md`，数据版本 `extended_dapo_v2`）。
  - GPQA 只用于检查是否退化。0.6B 模型很可能接近随机水平（25%），且只有 198 题。
  - 平均方式在看到结果前确定，不根据模型表现挑选任务。
- **长度：**8k 为主口径；最终候选补评 16k；同时报告平均输出长度。16k 会改变方法之间的排序（例如旧 GAD − 旧 SeqKD 在同一批样本上从 8k 的 +1.99pp 变为 16k 的 +0.69pp），不能只看单一长度。
- **统计分辨率：**辅助监督的预期效果很可能在 1–2pp 以内，单 seed 的正式实验大概率无法得出结论。建议二选一或同时采用：
  - 每个方法至少 2 个训练 seed；
  - 在成功标准中加入 Critic 侧指标，即第 2 节的同题排序准确率（在正式实验的 Critic 上重新计算），不只看 Actor 分数。
- 截断比例和正常结束后的正确率只作为诊断，不单独用来判断方法优劣。

## 4. 建议的执行顺序

| 顺序 | 任务 | 依赖 | 资源 |
| --- | --- | --- | --- |
| 1 | 第 2 节：Critic 同题排序诊断 | 无 | GPU（只推理） |
| 1 | 原方案第 7 节第一步：direct_v1 实现与 CPU 回归 | 无，与诊断并行 | CPU |
| 2 | 原方案第 7 节第二步：固定 32 条，加入 3.2–3.4 节的修改 | 实现完成；预算放宽经用户确认 | GPU |
| 3 | 原方案第 7 节第三步：Warmup 12 步 → GAD 4 步与保存恢复探针，报告 3.3 节交叉表 | 固定 32 条通过 | GPU |
| 4 | 正式实验 | 用户确定数据；诊断结果支持继续 | GPU，由用户安排 |

API 数据试点可以与以上各步并行，由用户安排。

## 5. 不做的事

- 不因诊断结果自行修改奖励通路、每题采样数或损失定义。这些属于新的实验设计，需要先与用户讨论。
- 不修改已完成 run 的 checkpoint、配置、评测结果或训练身份。合并后的 Critic 放在独立目录。
- 不自动启动正式训练或完整评测，也不执行全局 GPU / Ray 清理。
- 不扩展 Judge 协议：原方案第 8 节的约束全部保留，包括不增加多模型投票、动态 rubric 和自动标签修复。
